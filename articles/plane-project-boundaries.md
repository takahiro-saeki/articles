個人開発のリポジトリが増えると、タスクの置き場所をディレクトリ名で決めたくなります。ただ、修正用のworktreeまで別プロジェクトとして扱うと、同じアプリの未完了作業が散らばります。

手元のSquadNoteには、`circle-hub-multi-device-push`や`circle-hub-android-safe-area-hotfix`など、修正の目的ごとに分かれた作業ディレクトリがあります。一方、Plane側には`SquadNote`という一つのProjectがあります。通知の不具合もAndroidの表示修正も、利用者から見れば同じサービスの変更です。

この記事では、2026年9月11日に確認した個人WorkspaceのProject一覧とリポジトリの記録を使い、タスクの所属先を決める基準を整理します。すべての個人開発をPlaneへ移行済みという話ではありません。

## 最初に、実際に存在するProjectを調べる

個人Workspaceで一覧取得を行うと、次の5件が返りました。先頭ページだけで判断せず、次のページがないことも確認しています。

| Project | 識別子 | 一覧と手元の資料から確認できた対象 |
| --- | --- | --- |
| SquadNote | SQN | サークル管理サービス。リポジトリ名は`circle-hub` |
| SLABYRINTH | DRG | ゲーム。リポジトリ名は`dungeon-roguelite` |
| meguri | MEG | 振り返り・グループワーク・コーチングのサービス |
| Recital Originals 2026 | RECITAL | オリジナル楽曲の制作 |
| hiro work | HIROW | 説明文にPlaneのデモ用Projectと記載 |

記事専用のProjectは、この一覧にはありませんでした。`hiro work`という名前だけを見て、「分類前のアイデアを全部入れる場所」と決めることもできません。Workspaceと同名のProjectであっても、説明を確認する必要があります。

Planeの[Projectの公式説明](https://docs.plane.so/core-concepts/projects/overview)では、ProjectはWorkspace内の作業をまとめる単位で、識別子がWork Itemの番号に付きます。Gitのリポジトリやworktreeとの一対一対応を必須にはしていません。

## 同じサービスの作業コピーは、同じProjectへ戻す

SquadNoteの複数端末Push対応には、リポジトリ内に`docs/multi-device-push.md`があります。文書の冒頭にある対象チケットは`SQN-49`です。修正用ディレクトリの名前が長くても、作業の所属は`SQN`に戻れます。

作業場所が増えても、この対応を辿れば同じProjectへ戻れます。

```text
SquadNote / SQN
  ├─ circle-hub
  ├─ circle-hub-multi-device-push
  └─ circle-hub-android-safe-area-hotfix
```

これはProjectの構成を説明するための図です。Planeがディレクトリを自動検出して結び付けているわけではありません。

新しい修正が「別のプロダクトなのか」「既存プロダクトの変更なのか」を先に決めます。後者なら、作業用ブランチ名やディレクトリ名をWork Itemの本文へ残せば足ります。Projectまで新設すると、リリース前に見るべき一覧が増えます。

たとえばPushの修正はWeb側の登録APIとモバイル側のログアウトをまたぎます。WebとiOSを別Projectに分けるより、同じ変更の完了条件として「両方の変更が必要」と書くほうが、この作業には合います。別々に保守する体制になった場合は、改めて境界を見直せます。

## 製品名とリポジトリ名が違っても、無理に揃えない

SLABYRINTHのREADMEには、製品名を決めたあとも`dungeon-roguelite`を開発用識別子として維持する記録があります。PlaneのProject名は`SLABYRINTH`、識別子は`DRG`です。

名前をすべて同時に変更しなくても、対応が書いてあれば作業できます。逆に、製品名しか記載していないと、コードを探す段階で迷います。Projectの説明には製品名とリポジトリ名を併記し、リポジトリのREADMEからリリース用チケットの文書へ辿れるようにする。この程度の相互参照でも、名称変更後の入口を残せます。

製品名、リポジトリ名、チケットの識別子は役割が違います。表示名を変えたことだけを理由に、過去のタスクを別Projectへ移す必要があるかは、作業範囲を見て判断します。

## まだ所属先のない作業は、勝手に既存Projectへ押し込まない

このリポジトリの記事制作には、候補一覧と制作進捗表があります。しかし、確認時点のPlaneには対応するProjectがありません。

その場合の次の運用は、記事制作を今後も独立して継続するかで決める設計にします。継続するなら記事専用Projectを検討し、単発のメモなら原稿リポジトリの候補一覧で管理する。これは今後の選択肢で、今回すでにProjectを作ったという記録ではありません。

同じ理由で、デモ用ProjectをInboxだと見なして新しい作業を入れません。名前が汎用的なことと、投入先として決めてあることは別です。

新規タスクは、次の順に所属先を確認します。

1. 既存のサービスやゲームに対する変更なら、そのProjectを使う。
2. リポジトリ名が違う場合は、READMEとProjectの説明で対応を確認する。
3. 対応先がなければ、継続的な成果物かを確認してから置き場所を決める。

## この調査で分かったことと、まだ分からないこと

一覧とリポジトリの記録から確認できたのは、プロダクト単位のProjectが存在し、少なくともSquadNoteとSLABYRINTHにはコード側からチケットへ辿る手掛かりがあることです。タスクを探す時間が何分減ったか、未完了件数が減ったかまでは計測していません。

また、今回の境界は個人Workspace内の整理です。会社の情報を同じWorkspaceへまとめる提案ではありません。

手元の作業ディレクトリを一つ追加するたびにProjectを増やす必要はありません。通知修正の完了を判断したいときに見る先が`SquadNote / SQN`で変わらないこと。その対応を、Planeの説明とリポジトリの文書の両方へ残すのが、ここで採る基準です。
