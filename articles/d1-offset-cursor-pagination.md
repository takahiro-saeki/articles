一覧の次ページを`LIMIT 20 OFFSET ...`で取得すると、SQLは短く書けます。ただ、後ろのページへ進むほど、返さずに読み飛ばす行が増えます。インデックスを使っているというだけでは、その読み飛ばしはなくなりません。

通知一覧を模した10万行をローカルD1へ入れ、OFFSETとカーソルで同じ20件を取得しました。調べたいのは、どこまで読み取るかと、ページをまたぐ間に新しい行が入ったときの違いです。

確認日は2026年9月11日です。これはローカル実験であり、本番D1の遅延、料金、何件から必ず遅くなるかを示す測定ではありません。

## 同じ順番を再現できるキーを用意する

実験のテーブルは次の形です。

```sql
CREATE TABLE notification (
  id INTEGER PRIMARY KEY,
  user_id TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_feed
  ON notification(user_id, created_at DESC, id DESC);
```

`user-a`の通知を100000行作り、`created_at`にはIDを3で割って整数にした値を入れました。同じ時刻の行が存在するデータです。

並び順は`created_at DESC, id DESC`にします。時刻だけでは同時刻の行を一意に並べられないため、IDまで順序とカーソルへ含めます。この例は両方の列が`NOT NULL`で、IDが一意という前提です。

[SQLiteのRow Valuesの説明](https://www.sqlite.org/rowvalue.html)では、複数列を一つの比較として扱う書き方と、スクロールする一覧への応用が示されています。今回はそれをD1のSELECTで確認しました。

## OFFSETとカーソルで、同じ20件を取り出す

OFFSET側は、指定した件数を先頭から飛ばします。

```sql
SELECT id, created_at
FROM notification
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET ?;
```

カーソル側は、直前ページの最後の行より後ろを探します。降順なので比較は`<`です。

```sql
SELECT id, created_at
FROM notification
WHERE user_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

二つのカーソル値には、直前ページの最後の`created_at`と`id`を渡します。`created_at < ?`だけにすると、境界と同じ時刻の残りの行を飛ばす可能性があります。

測定ではOFFSETが20、1000、10000、50000、99000の位置を選び、比較用にそれぞれの直前の行を先に取得しました。このカーソルの取得時間は測定へ含めていません。実際の「次へ」では直前ページの結果から持ち越す値ですが、任意のページ番号へ直接飛ぶ処理とは同じ条件ではありません。

## 読取り行数は、返った件数と大きく違う

全条件でIDと時刻の配列が一致し、返る件数は20件でした。最後の計測クエリが返した`meta.rows_read`は次のとおりです。

| OFFSETの位置 | OFFSETの読取り行数 | カーソルの読取り行数 |
| --- | ---: | ---: |
| 20 | 40 | 23 |
| 1000 | 1020 | 22 |
| 10000 | 10020 | 22 |
| 50000 | 50020 | 23 |
| 99000 | 99020 | 21 |

カーソルも常に20行だけ読むわけではありませんが、このデータでは21〜23行でした。OFFSET側は、位置に応じて読取り行数が増えています。

`EXPLAIN QUERY PLAN`では、両方とも同じcovering indexを使っていました。関連する出力は次の形です。

```text
OFFSET:
SEARCH notification USING COVERING INDEX idx_feed (user_id=?)

Cursor:
SEARCH notification USING COVERING INDEX idx_feed (user_id=? AND created_at<?)
```

インデックスを使ったかだけでなく、どの条件から検索を始めるかを見る必要があります。`id`まで含めた比較の結果が正しいことは、実際に返った配列の一致でも確かめています。

[D1のインデックス公式資料](https://developers.cloudflare.com/d1/best-practices/use-indexes/)も、返る行数と読み取る行数を区別し、`EXPLAIN QUERY PLAN`や`meta.rows_read`で調べる方法を説明しています。表の数値はローカルMiniflareの値で、本番請求額の計測へ読み替えません。

## 時間も測ったが、一つの境目は決めない

実行環境はmacOS/arm64、Apple M4 Max、Node.js `v24.15.0`、Wrangler `4.81.1`、Miniflare `4.20260409.0`です。設定ファイルには互換日`2026-09-11`を指定しました。ただし、この版の`getPlatformProxy`は生成するWorkerへその日付を渡していません。測定対象はこのローカルD1実装であり、指定日のWorker動作を検証した結果ではありません。リモートbindingは無効、永続化なしで使いました。

各位置で4回のウォームアップ後、11回を測定しました。OFFSETとカーソルの実行順を交互に変え、`performance.now()`で`.all()`の待機を含む時間を測っています。ローカルproxyの呼び出し時間は含み、カーソルの準備と結果のassertは含みません。

| OFFSETの位置 | OFFSET中央値 ms | カーソル中央値 ms |
| --- | ---: | ---: |
| 20 | 1.435 | 1.219 |
| 1000 | 1.113 | 0.990 |
| 10000 | 1.026 | 1.084 |
| 50000 | 1.809 | 1.123 |
| 99000 | 2.971 | 1.137 |

浅い位置では呼び出しの揺れもあり、10000の位置では中央値が逆転しています。最初の位置のカーソルでは、最大9.911 msの測定もありました。表だけから「10000件で切り替える」といった共通の境目は決められません。

この実験で明瞭なのは、OFFSETが深くなるにつれて読む行数が増え、今回の深い位置では所要時間にも差が出たことです。本番の移行判断には、実データの分布、ページサイズ、利用頻度、目標の応答時間で測り直す必要があります。

## ページの間に挿入すると、OFFSETでは一つ重なる

静止した一覧だけでなく、最初の20件を取得した後に、新しい先頭行を1件追加しました。

最初のページの最後はID`99981`です。追加後に`OFFSET 20`で次を取ると、その`99981`が再び先頭に出ました。先頭への挿入で、以前の20番目が21番目へ押し出されたためです。

保存したカーソルから取得した場合、次の先頭は`99980`で、前ページとのID重複はありませんでした。この結果もassertしています。

ただし、カーソルは一覧全体を固定するスナップショットではありません。並び順に使う値を途中で更新する場合や、削除された行も含めて同じ一覧を再現したい場合は、別の条件が必要です。今回の途中変更の検証は、先頭への1件の挿入に限ります。

## 「次へ」が欲しい一覧から適用を考える

カーソル方式では、次の位置を表す値を前ページから受け取ります。ページ番号を指定して一気に飛びたいUIでは、位置を別途探す必要があります。この実験でカーソルの準備を測定から外したのも、その違いを隠さないためです。

[再現コード](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/d1-pagination.mjs)にはデータ作成、配列一致、検索計画、測定値、途中挿入の検証が入っています。インデックスを使うかに加えて、返る結果と、次ページへ進むために読む範囲を確かめられます。
