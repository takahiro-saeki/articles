AIとの開発チャットをまとめると、読みやすい制作記の下書きができます。ただ、会話中の「対応した」「確認した」「全部通った」は、そのまま記事の事実にはできません。提案、コードの追加、テストの成功、実際のプレイは、それぞれ違う出来事だからです。

制作記へ移す前に、一文が何を主張しているかを分け、その主張を確認できる資料へ戻します。この記事ではVOLT NOMADのリポジトリに残る制作記の下書きと検証コードを使い、特に数字の単位と完了状態を確かめます。

確認日は2026年9月11日、対象は`game-jam-lab`のコミット`f074703`です。複数チャットの発言をすべて照合した記録ではなく、チャットの要約を公開原稿へ変える際にも使える検証手順です。

## 下書きを、主張の一覧として読む

[制作記の下書き](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/docs/DEVLOG_DRAFT.md)には、攻略順の検査、日英の物語テキスト、最終確認に関する記述があります。ただし冒頭で、最終の通しテスト後に結果を追記する下書きだと明示されています。

末尾には、通常エンディングまでの時間、全ルートの時間、最終修正、リリース候補の日付を書き込むための欄も残っています。この状態の文章を、公開済みの振り返りとして引用することはできません。

読む際は、文章の流れをいったん外し、次のように主張単位へ分けます。

| 下書きから確認したいこと | 戻る資料 | 記事に書くために必要な区別 |
| --- | --- | --- |
| 攻略順を1,440通り検査した | テストコードと監査文書 | 状態遷移のケース数か、人間のプレイ回数か |
| 日英の物語イベントが33件ある | カタログとその検査 | 項目の存在か、翻訳品質の評価か |
| 最終確認を終えて公開できる | 下書きの残項目とリリース記録 | 計画か、実施済みの結果か |

チャットの完了報告が見つかった場合も、まずこの一覧に追加します。報告の文体を整えるのは、その後です。

## 「1,440通り」は何を数えているか

[リリース監査コード](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/godot/tests/release_audit.gd)の`audit_every_hunt_order`を見ると、ステージ順の並べ替えを作り、それぞれについて最初に選ぶボスを変えています。

対象のカタログにはステージが6件、通常のボスが2件あります。したがって、順序は`6! = 720`通り、そこへ最初のボス選択を掛けると`720 × 2 = 1,440`ケースになります。

数字の意味を短いJavaScriptで表すと、次の形です。これは説明用にカタログを記号へ置き換えた例です。

```js
function permutations(items) {
  if (items.length === 0) return [[]];
  return items.flatMap((item, i) =>
    permutations(items.filter((_, j) => i !== j))
      .map(rest => [item, ...rest])
  );
}

const orders = permutations(["A", "B", "C", "D", "E", "F"]);
const cases = orders.flatMap(order =>
  ["boss-a", "boss-b"].map(firstBoss => ({ order, firstBoss }))
);
console.log(orders.length, cases.length);
// 720 1440
```

今回の[検証スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/game-submission-evidence.mjs)では、固定コミットの実カタログからIDを取り出して計算し、重複のない組み合わせが1,440件になることを確認しました。実行環境はNode.js `v24.15.0`です。

ただし、この再計算はGodotの監査テストを再実行したことにはなりません。確認したのは、ケース数の由来と組み合わせの数です。

## テスト名の次に、実際に呼んでいる処理を見る

監査コードは各ケースで新しいルート管理オブジェクトを作り、ステージの選択・完了、ボスの撃破、次のルートへの継続などのメソッドを呼びます。途中の状態や、保存用スナップショットから復元した状態も確認します。

ここでステージを完了させるのは、ゲーム画面を開いて敵のHPが尽きるまで遊ぶ処理ではありません。ルート管理の完了メソッドを呼び、状態が期待した遷移先になったかを調べています。

したがって、制作記には次のように書けます。

> 監査コードは、ステージの攻略順と最初のボス選択を組み合わせた1,440ケースについて、ルートの状態遷移を確認する構造になっている。

一方、「1,440回の通しプレイを行い、ゲーム全体に問題がないと確認した」と書くと、検査対象が広がってしまいます。描画、入力の手触り、戦闘中の挙動、実際の所要時間は、このループだけでは確認できません。

33件の物語イベントについても同じです。コードはイベント数や日英フィールドなどを確認しますが、そのassertだけで文章の自然さや翻訳の品質が保証されるわけではありません。存在確認の結果を、内容評価の結果へ変えないようにします。

## 文書間で時点が違うときは、未確認を残す

[リリース候補の監査文書](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/docs/RELEASE_CANDIDATE_AUDIT_2026-08-12.md)には、その時点の自動確認やブラウザ確認の記録があります。一方、制作記の下書きには人手の通し確認を追記する欄が残っています。

この差を、都合のよい方の文書で埋めません。監査文書に記録された確認と、制作記がまだ求めている確認の範囲を、それぞれ読む必要があります。今回の記事調査では新しい通しプレイや公開ページの動作確認を行っていないため、それらの現在の結果は追加しません。

制作過程を復元するなら、採用する主張ごとに次の情報を控えます。

```text
主張: 攻略順とボス選択のケース数は1,440
根拠: 固定コミットのカタログと監査コード
今回の確認: 組み合わせ数を別スクリプトで再計算
今回の対象外: Godotの監査実行、通しプレイ、所要時間
原稿での表現: 状態遷移テストのケース数として説明
```

この小さな記録があると、編集で一文を短くしても、「対象外」を誤って完了実績へ変えたかどうかを見直せます。

## 読み物へ戻すのは、確認できた主張だけ

確認後は、チャットの順番を再現するより、読者の疑問に沿って並べ直せます。今回なら「数字が大きい」から始める必要はなく、「どの状態遷移を漏らしたくなかったか」「どう組み合わせを作ったか」「何は別に確認する必要があるか」の順に説明できます。

資料に記録されていない感想や手作業は、一人称の体験として補いません。「何度も遊んで手応えを得た」といった体験は、コードやテスト名からは復元できません。

AIに下書きを整理させるときも、確認済みの主張、参照資料、未確認の範囲を一緒に渡します。今回の1,440という数字なら、「通しプレイ回数へ言い換えない」まで指定できます。文章を自然にする編集と、事実として言える範囲を広げることを、別の作業として扱えます。
