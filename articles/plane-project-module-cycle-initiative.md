Planeの整理単位を階層として全部使おうとすると、一人で一つの機能を作るだけでも入れ物が増えます。選ぶときの基準は、「いま何の完了を確認したいか」に置くと分かりやすくなります。

サービスの保守ならProject、機能や版の完了ならModule、期間内の作業ならCycle、複数Projectで達成する目的ならInitiativeです。ただし、これらを一列に並ぶ必須の階層として扱う必要はありません。

以下は2026年9月11日にPlaneの公式ドキュメントを確認し、SquadNoteの複数端末Push対応を当てはめた設計案です。確認したWorkspaceでは専用のInitiatives機能が無効で、SquadNoteの非アーカイブのModuleとCycleはどちらも0件でした。後半の配置例は、導入済みの運用実績ではありません。

## 一つの変更を四つにコピーしない

複数端末Push対応には、トークン登録、ログアウト、送信対象の選定、端末での受信確認があります。リポジトリには、この仕様と検証条件をまとめた`docs/multi-device-push.md`があり、`SQN-49`に紐付いています。

この作業を例にすると、それぞれの単位で答えたい問いは次のようになります。

| 単位 | 答えたい問い | 配置を考える場合の例 |
| --- | --- | --- |
| Project | どのサービスの作業か | SquadNote |
| Module | どの成果物が揃えば完了か | 複数端末Push対応 |
| Cycle | この期間に何を進めるか | 9月のある週に行う登録APIとログアウトの実装 |
| Initiative | 複数のProjectで何を達成するか | 複数アプリの通知運用を見直す |

最後の例は、複数アプリへ広げる必要が出た場合の仮案です。SquadNoteだけの変更ならInitiativeを増やす理由はありません。

同じ作業をProject用、Module用、Cycle用に別チケットとして複製する設計にはしません。どこか一枚だけがDoneになり、ほかに古い状態が残るためです。まず作業本体を一つ決め、そのWork Itemを必要な整理単位に関連付けます。

## Projectは保守の所属先として残す

[公式のProject説明](https://docs.plane.so/core-concepts/projects/overview)では、Project内にWork ItemやCycle、Moduleなどを置きます。

SquadNoteなら、Push対応を終えても認証や出欠管理の保守は続きます。そのため、今回の機能を完成させたことと、Project全体を閉じることは一致しません。

「複数端末Pushが終わったか」と「SquadNoteに未完了の作業があるか」は別の問いです。この二つを同じ状態一つで表現しようとすると、機能は終わっているのにProjectはずっと進行中、という表示だけが残ります。Projectを継続的な所属先と考えれば、その表示自体に問題はありません。

## Moduleには、成果物としての完了条件を置く

[Moduleの公式説明](https://docs.plane.so/core-concepts/modules)では、機能などのまとまりにWork Itemを関連付けられます。開始日や期日も設定でき、一つのWork Itemを複数のModuleへ所属させることもできます。

複数端末PushをModuleにするなら、「通知を改善する」だけでは完了を判断できません。実装文書を元に、たとえば次の条件へ具体化できます。

- 同一ユーザーのiOSとAndroidのトークンを同時に保持できる。
- 一方の端末からログアウトしても、もう一方の登録は残る。
- 通知をONにした対象ユーザーの登録端末へ送信処理が向く。
- 本人の検証用端末で、実際の受信結果を記録する。

最初の項目だけ終わっても、Module全体の完了にはしません。サーバーに保存できたことと、端末が受信できたことを区別するためです。

機能のまとまりをさらにアプリの版にも関連付けたいなら、機能ModuleとリリースModuleを併用する選択肢があります。ただ、一枚のWork Itemにまとめられる規模なら、最初からModuleを作る必要はありません。

## Cycleの終了日は、機能の完成日とは限らない

[Cycleの公式説明](https://docs.plane.so/core-concepts/cycles)では、Cycleは一定期間の作業をまとめる単位です。期間を終了しても未完了のWork Itemは残り、次のCycleへ移す操作があります。

たとえば、今週は登録APIとログアウトを変更し、実機受信は来週行うとします。今週のCycleは終わりますが、「複数端末Push対応」の完了条件はまだ満たしていません。

この場合、Cycleの終了に合わせて機能Moduleまで完了扱いにすると、端末検証が見えなくなります。機能Moduleの条件は維持し、未完了の検証だけを次の期間に扱うほうが、残作業を説明できます。

逆に、Moduleにも期日が付けられることを理由に、すべての週次計画をModuleで表現する必要はありません。成果物の名前を付けたいのか、その期間に進める量を決めたいのかで選びます。

## Initiativeは、横断する目的があるときに検討する

[Initiativesの公式ページ](https://docs.plane.so/core-concepts/projects/initiatives)は、複数の関連Projectを共通の目的の下で追跡する機能として説明し、Proの表記と有効化手順を載せています。

確認した個人Workspaceでは専用機能が無効でした。MCPの応答には同名のWork Item型を使う案内もありましたが、それを専用のInitiatives機能を導入済みである証拠にはしません。同じ名前でも、使う機能と関連付けられる対象を確認する必要があります。

設計としては、「個人開発を頑張る」ほど広い目的を付けると、どのProjectを含めるかも、いつ完了にするかも決まりません。「対象アプリの通知解除手順を揃え、それぞれで受信確認を終える」なら、対象Projectと完了条件を列挙できます。これは利用価値が生まれる場面の例であり、複数アプリの作業を今回実施したという意味ではありません。

## 一枚のWork Itemから始める

SquadNoteでは、Projectと具体的なWork Itemから実装文書へ辿れました。ModuleやCycleを使わないと作業できない状態ではありませんでした。

まず一枚のWork Itemへ完了条件を書きます。関連する作業が増え、成果物全体の完了を見たくなったらModuleを検討する。週の計画と持ち越しを確認したくなったらCycleを使う。さらに複数Projectを一緒に判断する目的ができた段階でInitiativeを検討する。この順序は、今回の個人開発に当てはめた提案です。

分類を増やした効果や継続率は、まだ比較していません。まずはPush対応の「APIの変更は終わったが、端末受信の確認は残る」という状態を、チケットの完了条件だけで表現できるかを確認するところから始められます。
