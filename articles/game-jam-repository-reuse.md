Game Jamが終わった後に残したいのは、ゲームのソースだけではありません。提出用ZIPの作り方、使った書き出しプリセット、テストの起動方法も、次のイベントで読み直せると助かります。

ただし、前回のゲームを保存することと、次回へ持ち出せる共通ライブラリを作ることには距離があります。`game-jam-lab`を調べると、イベントごとに資料とツールを閉じる構造はありますが、すべてのイベントで使う共通SDKが完成しているわけではありませんでした。

この記事では、イベントを増やせるディレクトリ構造を保ちつつ、テストと書き出しがどのゲームを対象にするかを明示する設計を考えます。確認したのは2026年9月11日時点のコミット`f074703`です。進行中の未コミット作業を、完成済みの機能として数えていません。

## まず、提出単位で一式を辿れるようにする

[コミット済みの構造](https://github.com/takahiro-saeki/game-jam-lab/tree/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4)を関連部分だけにすると、次の形です。

```text
events/
  2026-ai-browser-game-jam-4/
    godot/
      project.godot
      shared/
      tests/
    docs/
    tools/
    submission/
```

このコミットに追跡されているイベントは1件です。複数イベントを運用し終えた実績ではなく、次を追加できる入れ物として評価します。

イベントの下にゲーム、設計資料、ツール、提出資料があると、「どの提出物のためのスクリプトか」をパスから辿れます。リポジトリ直下に複数作品の`project.godot`や提出ZIPの処理を混ぜる構成より、前回分を残したまま次を追加する場所がはっきりします。

一方、フォルダをコピーするだけで次の提出ができるとは限りません。イベント名、ゲーム名、書き出しプリセット、公開先は別に確認する必要があります。保存場所を分けることは、これらを自動で切り替える仕組みの代わりにはなりません。

## スクリプトの場所から対象を求める

[itch.io向けの書き出しスクリプト](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/tools/build-itch-project-charge.sh)は、実行したときのカレントディレクトリではなく、自分自身の場所からイベントのルートを求めています。

```bash
script_dir="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
event_root="$(cd "$script_dir/.." && pwd)"
godot_root="$event_root/godot"
output_dir="$event_root/build/itch/volt-nomad"
archive_path="$event_root/build/itch/volt-nomad-web.zip"
```

`godot_root`が確定してから、`--path`へ渡します。出力先も同じイベントの`build/`の下です。リポジトリ直下で実行しても、イベントの中から実行しても、対象が変わらない書き方になっています。

これは「次のイベントにもそのまま使える」という意味ではありません。`volt-nomad`という出力名と`Itch Volt Nomad`というプリセット名はゲーム固有です。次回へコピーするとき、変更する値が残っています。全部を汎用化する前に、まず変更が必要な固有値を読み取れるようにします。

## パスとZIPの構造だけを分離して検証する

この設計を確認するため、固定コミットの実スクリプトを一時ディレクトリへ取り出しました。イベントフォルダ名は検証用に変え、Godot実行ファイルの代わりに小さなスタブを置きます。

スタブは渡された引数を保存し、`index.html`、`index.js`、`index.pck`、`index.wasm`という検証用ファイルを作るだけです。Godotによるゲームの書き出しは行いません。ZIPを作り、必須ファイルを確認するシェルの処理は元のものを動かしました。

| 実行場所 | `--path`の対象 | ZIP直下の4ファイル |
| --- | --- | --- |
| 検証用リポジトリのルート | そのイベントの`godot/` | すべて確認 |
| そのイベントの`godot/` | そのイベントの`godot/` | すべて確認 |

`bash -n`の構文確認も通っています。[検証コード](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/game-jam-layout.mjs)はNode.js `v24.15.0`で実行しました。

```bash
node experiments/article-stock-2026-09/game-jam-layout.mjs ../game-jam-lab
```

これで確認したのはパスの組み立てとZIPの構造です。ゲームが起動すること、Web書き出しが成功すること、itch.ioで動くことは別の検証です。対象のCIはGodot `4.6.2`を指定していますが、この実験でGodotを実行したわけではありません。

## `shared/`が共有する範囲を読み違えない

対象イベントの`godot/shared/`には、コントローラー入力、パレット、音声設定、シンセサイザーなどのファイルがあります。ただし、これらはイベントの内側にあります。リポジトリ直下の共通`tools/`や、イベントを跨ぐライブラリとして抽出された構造ではありません。

この違いは、次のゲームで再利用するときに効きます。イベント内の共有コードなら、同じゲーム群の名前や設定を知っていても困りません。別イベントへ持ち出すには、入力アクション名や保存先など、元のゲームへの依存を確認する必要があります。

今後の案としては、最初から全イベント共通に移すより、次のイベントでコピーして使ったときに差分を見ます。毎回変える値がゲーム名だけなら、引数や設定に出せるかもしれません。ゲームの進行や素材まで書き換えるなら、その部分はイベントに残す方が読みやすいでしょう。

共通化の判断材料は、名前が`shared`かどうかではなく、二つのイベントで何を変えずに使えたかです。この比較はまだ実施していないため、共通化によって作業時間が減ったという数値は出せません。

## イベントを追加したら、CIの対象を別に選ぶ

[Pages用workflow](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/.github/workflows/pages.yml)では、スモークテストとWeb書き出しの`--path`が`events/2026-ai-browser-game-jam-4/godot`に固定されています。`events/`の全フォルダを見つけて実行する仕組みではありません。

したがって、次のイベントのフォルダを追加しても、それだけでは次のゲームがテストされることにはなりません。テストする対象、公開する対象、保管だけする対象を、workflow側で選ぶ必要があります。

ここを将来変更するなら、検証対象を列挙する設定と、公開対象を一つ選ぶ設定を分ける案が考えられます。古いイベントも構文や起動を確認したい一方、公開先を新しいゲームで上書きするかは別の判断だからです。この案は対象コミットには実装されていません。

次回へ残せる状態にするには、イベントの一式を保存したうえで、そのスクリプトとCIが何を指しているかを確かめます。今回の構造では、書き出しスクリプトの相対的な配置は再利用できます。ゲーム固有の出力名と、固定されたCIの対象は、次回に選び直す項目です。
