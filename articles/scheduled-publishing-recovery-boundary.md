投稿スクリプトが失敗したとき、同じコマンドをもう一度実行してよいかは、失敗した場所によって変わります。外部サービスに記事が作られる前なら新規投稿を試せますが、作成後に応答だけ失われた場合は、もう一度記事を作る可能性があります。

このリポジトリの予約投稿は、Qiitaの`id`とdev.toの`devto_id`を原稿へ保存し、次回はそのIDを使って更新します。保存済みIDがある場合の再実行には対応しています。ただし、それだけで完全な重複防止にはなりません。

コミット`8a1bfa8`の投稿スクリプトを、外部APIとファイル操作をモックにした環境で動かし、どこまで復旧できるかを確認しました。この記事は確認した実装の説明と、残る穴を踏まえた復旧手順案です。重複公開事故が実際に発生したという報告ではありません。

## IDを保存できれば、次回は同じ記事を更新する

`scripts/publish-scheduled.mjs`は、指定日の予約を読み、日本語を処理してから英語を投稿します。Qiitaでは`id`があればPATCH、なければPOSTです。dev.toでは`devto_id`があればPUT、なければPOSTです。

```text
QiitaへPOST
  ↓ レスポンスからidを取得
日本語原稿へidを保存
  ↓
dev.toへPOST
  ↓ レスポンスからidを取得
英語原稿へdevto_idを保存
```

IDと公開済みフラグが両方の原稿に揃っている場合、スクリプトはAPIを呼ばず正常終了します。

日本語だけ完了している場合は少し違います。現在の実装はQiitaへの処理も通り直しますが、IDを持っているのでPATCHになります。その後、IDのないdev.toへPOSTします。「英語だけ再試行する」と説明すると実際の動きとずれるため、ここは区別しておきます。

## 定期起動と同じジョブ内の再試行は、役割が違う

予約workflowは、JSTの08:55に相当する起動と、09:10に相当する再起動を設定しています。早い起動では09:00まで待ちます。さらに一回のジョブ内で投稿スクリプトを最大3回試し、失敗後に30秒、60秒待つ構成です。

この再試行で、同じジョブのファイルへ保存済みのIDを使い回せます。別のrunに引き継ぐには、変更したfrontmatterがGitへ保存されている必要があります。workflowは`if: always()`のメタデータ保存工程を持っていますが、その工程の実行やpushが失敗した場合まで保証する仕組みではありません。

`concurrency`のグループも設定しています。同じグループのworkflow同士が同時に投稿するのを抑えるためのもので、外部サービスのPOSTに冪等性を与えるものではありません。

定期起動の時刻についても、GitHubは[高負荷時の遅延などを説明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)しています。再起動を設定したことと、希望時刻どおりに投稿できることは同義ではありません。

## 実際のスクリプトを、外部へ送らず検証する

検証日は2026年9月11日、Node.jsは`v24.15.0`です。[再現コード](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/publishing-recovery.mjs)はGitから対象スクリプトを読み、二つのimportを取り除いてVM内で実行します。代わりにファイルの読み書き、`fetch`、環境変数をテスト用の値で渡します。

```bash
node experiments/article-stock-2026-09/publishing-recovery.mjs
```

実APIへの通信は行いません。偽のサーバーはPOSTを受け付けるたびに記事数を増やし、受付後の応答消失も再現できます。偽のファイルは再実行の間に保持するので、ID保存後と保存前の違いを確かめられます。

| 最初の実行で起きたこと | 再実行時の呼び出し | 偽サーバー上の最終件数（Qiita / dev.to） |
| --- | --- | --- |
| 日英とも投稿し、IDを保存 | 呼び出しなし | 1 / 1 |
| QiitaのID保存後、dev.toが422 | Qiita PATCH、dev.to POST | 1 / 1 |
| Qiitaが受付後、応答を失う | Qiita POST、dev.to POST | 2 / 1 |
| dev.toが受付後、応答を失う | Qiita PATCH、dev.to POST | 1 / 2 |
| Qiitaが受付後、ローカル保存に失敗 | Qiita POST、dev.to POST | 2 / 1 |

別にdry-runも検証し、API呼び出し0件、偽サーバーの記事数も0件でした。合計6ケースの期待値をassertで確認しています。

この結果は実サービスがどの頻度で応答を失うかを測ったものではありません。スクリプトがどの情報を持って次のリクエストを選ぶかを検証しています。また、今回の偽サーバーはQiitaとdev.toの分岐を対象とし、Zenn側のGit連携反映や実際のGitHubジョブの待機は再現していません。

## 再試行する前に、IDを回復できるかを見る

上の結果から、運用での確認順序は次のように設計できます。

1. 対象日を固定し、dry-runで日本語パスと英語パスを確認する。
2. 失敗したrunのログと、原稿に保存されたIDを確認する。
3. タイムアウトなどで外部受付の成否が不明なら、媒体側の記事一覧や編集画面で作成済みの記事を探す。
4. 元記事と一致する投稿を特定できたら、その実際のIDと状態を回復してから再実行する。
5. 作成の有無を判定できない場合は、無条件のPOST再試行を止めて調査を続ける。

これは自動照合機能を実装したという説明ではなく、現在のスクリプトを使うための手順案です。タイトルだけで同じ記事と決めず、本文、対象日、canonicalなども照合します。IDを推測して埋めてはいけません。

dry-runは次のコマンドで実行できます。日付は確認対象に置き換えます。

```bash
node scripts/publish-scheduled.mjs --date=2026-08-04 --dry-run
```

このコマンドが示す公開済み状態はローカルのfrontmatter由来です。dry-run成功だけで、外部に未記録の記事がないと判断することはできません。

## 自動化を追加するなら、保存の境界から考える

今後の改善候補として、投稿処理の状態を`未送信`、`受付確認待ち`、`ID保存済み`のように記録し、受付確認待ちのままなら自動の新規POSTを止める方法があります。外部側との照合手順も必要です。

これは現行実装にはありません。ローカルへ状態を増やしても、外部で作成済みなのにIDを失う区間そのものは消えません。サービスが提供する冪等な作成方法があるか、または作成結果を確実に見つけられるかを別に調べる必要があります。

検証したコードでは、IDを保存できた失敗は更新としてやり直せます。外部受付後にIDを保存できなかった場合は、新規POSTへ戻り得ます。復旧時には「失敗した」という一つの状態へまとめず、この二つを分けて扱います。
