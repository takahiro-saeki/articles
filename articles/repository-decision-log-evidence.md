長い制作で困るのは、過去の案が見つからないことだけではありません。案は見つかったのに、それが採用済みなのか、まだ目標なのか、あとで変更されたのかが分からないこともあります。

VOLT NOMADの制作資料には、決定ログ、段階ごとの制作計画、公開候補の監査記録が残っています。これらをGitの同じ時点で読むと、目標と検証結果を区別できます。チャットの最後の発言だけで現状を決めないための、具体的な読み方です。

対象は`game-jam-lab`の`events/2026-ai-browser-game-jam-4/`です。2026年9月11日にコミット`f074703`の文書と履歴を確認しました。既存の制作記事では工程全体を紹介したので、ここでは「ある判断を次の作業者が復元できるか」に絞ります。

## 最初の決定ログには、選んだ内容と理由がある

`CHARGE_CLICKER_PRODUCTION_PLAN.md`には、日付、決定、理由の表があります。たとえば2026年8月2日の記録では、30秒、5分、20分の順で検証する方針が選ばれています。理由は、コアループの弱さを物量で隠さないためです。

機能や素材を大量追加したくなったら、この行へ戻れます。まず短いプレイが成立するかを確認する、という当時の方針が分かります。

ただし、同じ表にある「通常エンドを約20分」「真エンドは合計約1時間」は、プレイ時間の目標です。記録されているだけで実測値になるわけではありません。

表を読むときは、次のように分けます。

| 文書の記述 | 読み取れること | そこからは言えないこと |
| --- | --- | --- |
| 段階的に検証するという決定 | 当時選んだ検証方針 | 各段階のテストがすべて完了したこと |
| 約20分、約1時間という目標 | 当時の目指す体験時間 | 人がその時間でクリアしたこと |
| 日付と理由 | その判断の時点と意図 | 以後も変更されていないこと |

判断の履歴は、現在の状態を自動的に表すものではありません。

## 最新の完了状態は、別の記録と突き合わせる

同じディレクトリの`PROJECT_CHARGE_POLISH_PLAN.md`には、実装済み、音楽選定待ち、最終QA進行中など、工程ごとの状態が並びます。文書の更新日は8月6日です。

一方、8月12日の`RELEASE_CANDIDATE_AUDIT_2026-08-12.md`には、公開候補の自動検証結果があります。安定した入力モデルを2入力/秒とした場合、通常エンドは15.58分、完全ルートは23.26分という記録です。

最初の「約1時間」という目標と23.26分を並べて、「想定より大幅に短縮した」と判断するのは早すぎます。後者は自動入力の結果で、会話を読む、画面を理解する、強化を比較するといった時間を含まないと、監査文書に明記されています。

ここで復元できるのは、次の関係です。

```text
制作計画: 人が遊ぶ体験時間の目標
公開RC監査: 入力モデルを固定した自動プレイの結果
人の通しプレイ: 別の確認工程
```

この調査ではゲームの自動プレイを再実行していません。数値は保存されている監査結果の引用であり、新しい実測として扱いません。

## Gitの同じ時点を固定して読む

作業ディレクトリの最新ファイルだけを横断すると、途中の編集が混ざることがあります。説明や記事の根拠に使うなら、まずコミットを固定します。

```bash
git show f074703:events/2026-ai-browser-game-jam-4/docs/CHARGE_CLICKER_PRODUCTION_PLAN.md
git show f074703:events/2026-ai-browser-game-jam-4/docs/PROJECT_CHARGE_POLISH_PLAN.md
git show f074703:events/2026-ai-browser-game-jam-4/docs/RELEASE_CANDIDATE_AUDIT_2026-08-12.md
```

文書を変更した履歴を調べる場合は、対象ファイルを絞ります。

```bash
git log --oneline -- events/2026-ai-browser-game-jam-4/docs/CHARGE_CLICKER_PRODUCTION_PLAN.md
```

Gitのコミット日と、本文に書かれた決定日が同じであるとは限りません。あとから記録を追記することもあるため、判断の日付は本文、記録の差分はGitで確認します。どちらか片方を、すべての出来事の日時として使わないようにします。

今回の読み直しでは、初期方針、途中工程の状態、後日の監査結果がそれぞれ別文書に残っていることを確認できました。8月6日の「待ち」という記述を、そのまま9月時点の未完了一覧へコピーすることはできません。

## 次に残すログは、事実と提案を一行で区別する

既存の決定ログは日付、決定、理由の表です。そこからさらに読み戻しやすくするなら、状態と根拠を付ける形式を提案できます。

```markdown
## 判断: 短いプレイの検証を先に行う

- 状態: 採用した方針
- 決定日: 2026-08-02
- 理由: コアループの弱さを物量で隠さないため
- 根拠: CHARGE_CLICKER_PRODUCTION_PLAN.md の決定ログ
- 検証結果: 方針の採用とは別に記録する
```

これは既存ファイルへ導入済みの書式ではなく、元の記録を使って作った例です。新しいADR管理ツールを入れなくても、方針、実装、検証のどれを記録したのかは書き分けられます。

変更するときも、古い目標の数字を最新結果で黙って置換すると経緯が消えます。「以前の目標」「今回の条件での結果」「次に確認すること」を残したほうが、次の作業の入口になります。現在の方針だけ見たい読者には、READMEなどの入口から現行文書を案内します。

## チャットを残すことと、再開できることは同じではない

チャットには、案を選んだときのニュアンスが残ります。それをすべて捨てる必要はありません。ただ、次の作業に必要な判断が会話の途中にしかないと、コードのどの版に対応するかを追う必要が出ます。

リポジトリに置いた文書も、放置すれば古くなります。今回の資料にも、異なる日付の計画と監査が共存しています。文書があるだけで引き継ぎが完成するわけではありません。

再開時に確かめたいのは、「何を選んだか」「どこまで実装したか」「どの条件で確認したか」です。それぞれを辿れるファイルとコミットを残し、目標を実測に、途中の計画を最新の完了報告に読み替えない。この読み方なら、チャットをすべて再読しなくても、次に何を確かめるべきかを決められます。
