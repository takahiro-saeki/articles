Planeを個人で使うなら、無料のCommunity Editionを自分のサーバーへ置くほうがよいのでしょうか。比較するときは、月額だけでなく、壊れた管理環境を自分で戻せるかまで含めたいところです。

今回はCloudとセルフホストの提供範囲を公式資料で確認し、Community Editionの復元スクリプトへ模擬的な失敗を入れました。復元対象が足りない場合や復元処理が失敗した場合でも、スクリプトが終了コード0と成功の文言を返すケースがありました。

これはCloudとセルフホストの信頼性を測った実験ではありません。個人利用で選ぶ際に、**セルフホストの費用へ、復元結果を確かめる作業も含める**ための確認です。

## Cloud、Community、Commercialを混ぜない

2026年9月11日に[料金表](https://plane.so/pricing)と[Community Editionの説明](https://plane.so/open-source)を確認しました。CloudにもFreeがあり、Community Editionも無償ですが、同じ導入方法ではありません。

| 比較点 | Cloud | セルフホストCommunity Edition |
| --- | --- | --- |
| 基盤の運用 | 提供側が担うサービスを使う | 自分の基盤を運用する |
| 費用の入口 | Freeまたは必要な機能のプラン | ソフトウェアは無償。ホストや保存先は別 |
| 機能の確認 | Free / Pro / Businessなどを確認 | Communityで使える機能を確認 |
| 更新時の作業 | 自分のサーバーの更新作業は持たない | 設定、イメージ、DB移行、復旧手順を確認する |
| データ復元 | 利用者向けの復旧・取得条件を確認する | バックアップの取得と復元結果を自分で確認する |

たとえばCloudの料金表ではInitiativesはPro、Recurring Work ItemsはBusinessに入っています。これらを必要としている場合、Community Editionの「無料」だけを見ても機能要件を満たすとは決められません。

また、セルフホストCommercialには新規購入時の10席の最低数があり、Community Editionにはこの制限がないと[公式告知](https://forum.plane.so/t/new-seat-minimums-on-self-hosted-commercial-and-air-gapped-starting-april-24/96)で説明されています。一人用Cloudのプランを、そのまま一人用セルフホストCommercialの費用へ置き換えないようにします。実際の契約額やCloudの復旧対応時間は今回測っていません。

## インストール後に管理するものを読む

確認した[公式Compose定義](https://github.com/makeplane/plane/blob/2f895b82dad839c730c36a5c0cbc046f1e5d6b56/deployments/cli/community/docker-compose.yml)には13のservice定義がありました。Web画面、API、workerに加え、DB、Valkey、RabbitMQ、MinIO、proxyなどです。migratorも含む定義数なので、13台のサーバーが必要という意味ではありません。

このファイルは調査時のpreviewブランチをcommitで固定したものです。すべての安定版の構成が同じだとは扱わず、導入時には実際に選ぶ版の定義を読み直す必要があります。今回はPlane本体のコンテナを起動していません。

[バックアップと復元の公式手順](https://developers.plane.so/self-hosting/manage/backup-restore)は、DBとアップロードデータに加え、環境設定も保存するよう案内しています。Commercial向けPrime CLIとCommunity向けの手順も別です。

復元したDBが添付ファイルを参照していても、オブジェクト側が欠ければ元の状態には戻りません。環境設定の保管も含め、何を同じ時点へ戻すのかを決める作業が残ります。バックアップを同じホストだけへ保存すると、ホストを失ったときの復旧用コピーにはならない点も考慮します。

## 復元スクリプトを実行した範囲

[Communityのrestore.sh](https://github.com/makeplane/plane/blob/2f895b82dad839c730c36a5c0cbc046f1e5d6b56/deployments/cli/community/restore.sh)を変更せず、bashから実行しました。Python 3.14.5で一時ディレクトリを作り、そこでだけDockerコマンドを代役に置き換えます。

代役はボリューム一覧、作成、削除、復元コンテナの成否を返します。実際のDocker daemonへは接続しません。アーカイブもファイル名だけのfixtureであり、DBや添付ファイルを復元したテストではありません。

対象は、この版のスクリプトが扱う`pgdata`、`redisdata`、`uploads`、`rabbitmq_data`です。全件を用意した場合から一条件ずつ壊しました。

| 入力・失敗条件 | 復元コンテナの呼出し数 | 終了コード | 最後の成功文言 |
| --- | ---: | ---: | --- |
| 4種類のアーカイブとボリュームがある | 4 | 0 | あり |
| uploadsのアーカイブがない | 3 | 0 | あり |
| uploadsのボリュームがない | 3 | 0 | あり |
| uploadsの復元コマンドが失敗する | 4 | 0 | あり |

最後のケースは、途中に失敗の文言も出ています。それでも最終行には成功が出て、終了コードも0でした。自動処理が最後の一行や終了コードだけを見るなら、今回の欠落や失敗を見逃します。

この結果から、データが失われる頻度やPlane全体の復元成功率は出せません。観測したのは、固定したCLIの失敗の伝え方です。

## 成功表示の外側に何を置くか

ソースを読むと、アーカイブ欠落のケースでは、存在する`*.tar.gz`だけをループするため、不足している種類を要求しません。対象ボリュームがない場合はskipします。個別復元関数が失敗を返しても、呼び出し元はその戻り値でループ全体を失敗にしていません。

運用へ取り込むなら、まず自分の構成で必要なアーカイブを一覧化し、不足したバックアップを復元候補から外す必要があります。さらに、別の検証環境でDBを開き、代表的なWork Itemと添付を確認する段階が必要です。ファイル名が揃っているだけでは内容の正しさは証明できません。

これは今回導入した自動運用ではなく、実験結果から必要と判断した確認項目です。[再現スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/probe-plane-restore.py)には、実ボリュームを触らずに4条件のCLI分岐を追う方法を残しました。

復元後の確認を用意できても、更新前のバックアップが古ければ戻れる地点も古くなります。更新の頻度と保存期間、添付を含む保管量、別保存先の費用を、ホストの料金とは別に見積もります。今回の確認から具体的な月額や保守時間へ換算はしていません。

## 個人利用での選び方

目的が複数プロダクトの作業管理で、基盤保守へ使える時間を増やしたくないなら、必要な機能を満たすCloudのプランから比較できます。Cloudでも、データの取得方法や復旧依頼の条件は確認対象です。今回の実験はそのSLAを保証しません。

自分の基盤へ置く理由があり、更新前後の復元確認まで引き受けるなら、Community Editionを候補にできます。先に小さな検証環境で復元後の確認を一周させると、月額表に出ない作業が見えます。セルフホストを選ぶ前に、コンテナの起動に加え、必要な状態まで復元できることを確認します。
