EAS Updateで壊れたJavaScriptを配ってしまったら、自動で以前の版へ戻るのでしょうか。`expo-updates`にはerror recoveryがありますが、画面表示前後で試せる復旧が変わります。新しい更新を起動する処理と、以前の更新へ戻す処理も別です。

今回はiOSの`ErrorRecovery.swift`をそのままコンパイルし、外部との接続部分を代役にして7条件を実行しました。**error recoveryを端末データまで巻き戻す仕組みとして扱わず、どの起動候補を試せる状態なのかを確認します**。

## 実行したコードと、代役にした部分

検証日は2026年9月11日。Voices Diaryのローカル依存にある`expo-updates` 29.0.18を対象にしました。npmに記録されたgitHeadを使い、[Expo公式リポジトリの同じファイル](https://github.com/expo/expo/blob/45c60e10956764bbac6c62454890eeb25c74bbd6/packages/expo-updates/ios/EXUpdates/ErrorRecovery.swift)とbyte単位で一致することを確認しています。

macOS上でApple Swift 6.3.3をSwift 5言語モードにして実行しました。ErrorRecovery本体のタスク処理、DispatchQueue、タイマーは元のコードです。React Nativeのbridge、更新DB、ダウンロード、実際の再起動はテスト用の代役です。ログの出力先も一時ディレクトリです。

したがって、以下の「再起動」は`relaunch`の呼び出しを、「crash」は例外を投げるdelegateへの呼び出しを指します。iPhone上で更新を配信して、画面が復旧したことを確認した実験ではありません。

## 表示前なら新しい更新とキャッシュ済み更新を候補にできる

元の処理は、リモート更新を待つ、新しい更新を起動する、キャッシュ済み更新を起動する、例外を送出する、という候補を順に持ちます。状態に応じて候補を取り除きます。

まだ画面が出ておらず、その更新の過去の成功回数も0なら、起動失敗の記録を要求しました。新しい更新の準備ができているケースでは、新しい更新を起動するタスクから`relaunch`を呼びました。

新しい更新がなく、起動時の更新確認を`Never`にしたケースでは、キャッシュ済み更新を試すタスクへ進みます。代役が再起動失敗を返すと、最後に例外送出を要求しました。以前の版が必ず端末に残っていて、必ず起動できるという前提は置けません。

| 条件 | 元の処理が出した要求・選んだタスク |
| --- | --- |
| 表示前、過去成功0、新しい更新が準備済み | 失敗記録、新しい更新の起動要求 |
| 表示前、過去成功0、更新確認Never | 失敗記録、キャッシュ済み更新の起動要求 |
| 上と同じで再起動の代役が失敗 | 失敗記録、キャッシュ済み更新の起動要求、例外送出 |
| 今回のcontent appeared後、新しい更新が準備済み | 成功記録、例外送出。再起動要求なし |
| 表示前、過去成功1、更新確認Never | 例外送出。失敗記録と再起動要求なし |
| 表示前、過去成功1、新しい更新が準備済み | 新しい更新の起動要求。失敗記録なし |
| 表示前、過去成功0、更新確認がタイムアウト | 失敗記録、取得開始、キャッシュ済み更新の起動要求 |

タスク名は本体がloggerへ出したメッセージでも照合しました。同じ`relaunch`呼び出しだけを見て、新しい更新と古いキャッシュを区別したことにはしていません。

## 「今回表示した」と「過去に成功した」を分ける

今回の起動でcontent appeared通知を受けると、本体は成功記録を要求し、起動候補をリモート更新の待機と例外送出だけに絞ります。新しい更新がすでに準備済みでも、その場の再起動は要求しませんでした。

過去の成功回数があるだけの分岐は少し異なります。実装ではキャッシュ済み更新の起動候補を外しますが、新しい更新の候補はその分岐だけでは外しません。表の過去成功1・新しい更新準備済みのケースでは、その起動要求が出ました。

[公式のerror recovery説明](https://docs.expo.dev/eas-update/error-recovery/)は、今回または過去にcontent appearedが発生した場合をまとめ、新しい修正版を取得して次回起動へ備える流れとして説明しています。今回の版のソース実験では、上の二条件の即時再起動に違いがありました。ドキュメントの運用上の説明と、特定版の分岐を同じ粒度の保証にはできません。

どちらの状態でも、以前の成功版へ戻せると期待してはいけない点が判断に効きます。画面表示後には、保存データを新しい形式へ書き換えた可能性があるためです。古いJavaScriptを起動できることと、そのJavaScriptが現在の保存データを読めることは別に確認します。

## タイマーは「その秒数で必ず復旧」の約束ではない

対象ソースのリモート更新待機は5,000msです。実験も同じ値を使い、取得を開始したまま完了通知を返さずに待たせました。タイムアウト後、キャッシュ済み更新の起動要求へ進みました。

初回の検証器は5.2秒だけsleepして読み出す作りだったため、タスクの完了前に判定してしまいました。再起動要求の通知を待つ形へ直すと通りました。タイマーは期限以降に処理を実行するもので、OSのスケジューリングも含めて厳密な復旧時間を約束する値ではありません。

また、ソースにはcontent appearedから10秒後にエラーハンドラーを外す処理があります。今回の7条件では、この監視解除の時間境界は実測していません。起動直後のfatal JS errorを扱う仕組みの説明を、ネイティブクラッシュや長時間動作後のあらゆる障害へ広げないために区別しています。

## embedded updateへの指示は別の操作

EAS Updateには、公開済み更新へ戻す操作と、ビルド内のembedded updateへ戻す操作もあります。[公式のRollbacks](https://docs.expo.dev/eas-update/rollbacks/)にある配信側の指示であり、今回実行した端末内のerror recoveryの分岐そのものではありません。

この実験では更新DBも選択ポリシーも代役なので、どのupdate IDが選ばれたか、embeddedが選ばれたかは検証していません。`launchCached`というタスク名だけから「必ずembeddedへ戻る」とは書けません。

さらに、OTA更新はビルドのネイティブコードを差し替えません。[runtime versionの公式説明](https://docs.expo.dev/eas-update/runtime-versions/)が扱う互換性は、この境界にあります。存在しないネイティブ機能を呼ぶ更新の対策と、保存データの互換性、API側の互換性は、それぞれ別の確認が必要です。

## 自分のアプリで残す復旧テスト

[実行スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/probe-expo-error-recovery.py)には、公式ソースとの一致確認と7条件の期待値を残しています。端末上の配信や本番復旧を試すコードではありません。

アプリ側では、表示前の初回失敗、表示後の失敗、同じ更新が過去に成功した端末を分けて再現する必要があります。そのうえで、戻す候補が現在の保存データを読めるか確認します。復旧方針を決める根拠は、error recoveryが存在することより、その端末の履歴と状態で候補を実際に起動できることです。
