DBへ作成結果を保存した後に通知APIを呼ぶと、その間で処理が止まる可能性があります。DBにはデータがあるのに、通知すべきだったことを示す記録がありません。順序を逆にすると、今度は保存できなかったデータの通知が先に届く可能性があります。

Outboxパターンは、業務データと「後で配送するイベント」を同じDBトランザクションへ保存する方法です。ただし、それだけで外部への通知が一回になるわけではありません。

ローカルD1で、メモ作成とOutboxへの追加を同じbatchに入れ、送信成功後にconsumerが止まる経路も確認しました。確認日は2026年9月11日です。外部の通知APIは偽物に置き換え、実際の送信や公開環境への変更は行っていません。

## 先に、通知する意図をデータとして残す

[AWSのTransactional outboxの説明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)は、DB更新とメッセージ配送を別々に行うときの不整合を扱っています。同じトランザクションへ業務データとイベントを保存し、その後に配送する構成です。配送側の重複への対応も必要です。

今回の実験では、メモ本体の`note`と次の`outbox`を同じD1データベースへ置きました。

```sql
CREATE TABLE outbox (
  event_id TEXT PRIMARY KEY,
  note_id TEXT NOT NULL,
  kind TEXT NOT NULL CHECK(kind = 'note.created'),
  payload TEXT NOT NULL,
  sent INTEGER NOT NULL DEFAULT 0
);
```

`event_id`は配送を試すたびに作り直さず、保存したイベントを識別します。`payload`にはメモIDと、その時点のtitleをJSONで入れます。再送時に現在のメモを読み直す方法ではないため、同じイベントの内容を維持できます。

業務データとイベントの追加は、次の二つのINSERTを一つのbatchへ渡します。

```js
await db.batch([
  db.prepare('INSERT INTO note VALUES (?, ?, ?)')
    .bind(id, 'actor-a', 'hello'),
  db.prepare('INSERT INTO outbox(event_id,note_id,kind,payload) VALUES (?, ?, ?, ?)')
    .bind('event-'+id, id, kind, payload),
]);
```

これは[検証コード](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/d1-idempotency-outbox.mjs)からの抜粋です。D1の[batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)が扱うトランザクションは、このDB内の書き込みです。外部サービスへの送信まで同じbatchへ参加するわけではありません。

## イベント保存が失敗したとき、メモだけ残らないか

Outboxの`kind`には`note.created`だけを許すCHECK制約があります。そこへ不正な種類を渡し、二つ目のINSERTで失敗させました。

結果はメモ0件、Outboxも0件でした。先に実行したメモのINSERTまでロールバックされています。

正常な種類で作成すると、consumerを動かす前にメモ1件とOutbox1件が存在しました。その後にconsumerを呼ぶと、偽物の送信先へ1件が渡りました。業務データの作成と配送開始を分けても、配送するイベントをDBから取り出せることを確認しています。

これは単に通知用Promiseを後回しにした構成とは違います。配送を再開するための入力が、DBのレコードとして残ります。ただし、今回のローカル実験は永続化なしの環境であり、実プロセスやホストを再起動してストレージ耐久性を試したものではありません。

## 送れたのに、送信済みと書けない場所が残る

実験consumerの処理は次の順です。

```text
未送信イベントを一つ読む
event_idとpayloadを送信先へ渡す
送信成功を待つ
outbox.sentを1へ更新する
```

この最後の更新より前にconsumerが止まると、送信先では処理済みでも、Outboxには未送信として残ります。

テストでは、偽物の送信先が成功を返した直後に例外を投げました。次に同じDBに対してconsumerを呼び直すと、そのイベントをもう一度送ります。実プロセスを強制終了したのではなく、送信と記録の間の中断を例外で再現しています。

送信先に重複排除がない場合、呼び出しは2回、配送として数えた処理も2回になりました。Outboxの送信済みフラグだけでは、この区間の重複を防げません。

逆に、送信前に`sent`を1へするだけでは、送信自体が失敗したときに再送対象から消えてしまいます。フラグを立てる順序だけで、送信先とDBの二つの結果を原子的に揃えることはできません。

## 受信側が同じイベントを識別できると、再送をまとめられる

次は、同じ`event_id`とpayloadを受けたら既存の結果として扱う偽物の送信先を使いました。同じIDに異なるpayloadが来れば、テストは失敗するようにしています。

同じ中断を起こして再実行すると、送信先への呼び出しは2回でも、配送として数えた処理は1回でした。

| 条件 | DBまたは送信先の結果 |
| --- | --- |
| OutboxのINSERTで制約違反 | メモ0件、イベント0件 |
| 正常にコミットしてからconsumerを開始 | メモ1件、イベント1件、配送1件 |
| 送信成功後に中断、送信先の重複排除なし | 呼び出し2回、配送2件 |
| 同じ中断、送信先がevent_idで重複排除 | 呼び出し2回、配送1件 |

再試行後は`sent`が1になり、さらにconsumerを呼んでも次の未送信イベントがないことまで確認しました。

この送信先はNode.js内の偽物です。重複排除の記録に期限はなく、実在する通知サービスの保証を再現したものではありません。実装先では、受信側がどのキーを、どの期間、どの範囲で覚えるかを確認します。

受信側で一回にできない処理なら、重複があり得ることを前提に利用側の扱いを決めます。Outboxを導入したというだけで、配送までexactly-onceになったとは説明しません。

## 一つのconsumerの実験から、運用で必要なものを分ける

検証環境はNode.js `v24.15.0`、Wrangler `4.81.1`、Miniflare `4.20260409.0`です。D1のリモートbindingは無効にし、合成データと偽物の送信先を使っています。

consumerは一つだけを順番に呼ぶ実装です。複数workerが同じ未送信レコードを同時に選ぶ状況を防ぐclaimやlease、再試行間隔、失敗上限、DLQは実装していません。そのまま複数consumerへ増やしてよいという検証ではありません。

運用では、未配送イベントの件数、最も長い滞留時間、失敗理由を確認できるようにします。送信先が止まった場合はイベントを残して再試行し、対応が必要なものを調査できる状態にします。また、payloadの構造を変更する場合、古い未送信イベントを新しいconsumerが読めるかも確認対象です。

今回確認できたのは、DB更新と配送意図の同時保存、配送前のイベント取得、送信後・記録前の中断での再送です。Outboxが引き受けるのは、業務データだけが更新されて通知の意図が失われる隙間を埋めることです。その先の重複防止は、同じイベントを受け取る側まで含めて設計します。
