個人開発と会社の仕事を、一つのPlaneに入れたくなることがあります。画面を切り替えずに済み、今日の作業をまとめて見られるからです。

そのとき、Private Projectを作れば管理者からも独立した場所になる、と考えると分け方を誤ります。Projectを分ける前に、同じWorkspaceの管理者へ見せてよい情報かを確認します。

この記事は2026年9月11日に確認した公式ドキュメントに基づく設計案です。会社のWorkspaceへ接続した調査や、特定のPlane環境を移行した記録ではありません。実際の権限はエディション、ロール設定、導入バージョンを確認する必要があります。

## Private Projectでも管理者は別枠になる

[Projectの公式説明](https://docs.plane.so/core-concepts/projects/overview)には、Private Projectは明示的に招待されたメンバーに限定される一方、Workspace Adminはアクセスできると記載されています。

さらに[Member roles](https://docs.plane.so/roles-and-permissions/member-roles)では、Workspaceの旧AdminをOwnerへ改称したこと、OwnerがWorkspace全体へアクセスできること、AdminもProjectのメンバーに追加されずに内容へアクセスできることが説明されています。

公式ページ間でも新旧のロール名が混在しています。画面上のAdminという文字だけで結論を出すより、そのロールがWorkspaceを管理する立場か、Project内だけを管理する立場かを確認する方が確実です。

会社の管理者と共有したくない個人のタスクなら、会社WorkspaceのPrivate Projectへ置く設計は避けます。逆に、同じ管理者のもとで、普段参加する人や作業の流れだけを分けたいならProjectを使う余地があります。

## 分ける理由を、管理と作業に分けて書く

[Workspaceの説明](https://docs.plane.so/core-concepts/workspaces/overview)では、Projectを収める上位の単位であり、メンバーや連携の設定もWorkspaceで扱うとされています。

たとえば、次のように判断します。これは推奨する設計の例で、実環境に設定済みの一覧ではありません。

| 分けたい理由 | 検討する単位 | 決め手 |
| --- | --- | --- |
| 個人と会社で管理責任者が違う | Workspace | メンバーと管理権限を混ぜない |
| 同じ個人が管理するWebアプリとゲーム | Project | 管理者は同じで、作業対象が違う |
| 同じ組織で参加者を限定したい案件 | Private Project | Workspace管理者のアクセスは受け入れる |
| 関係者全体が参加できる改善活動 | Public Project | Workspace内で見つけて参加できるようにする |

「チケットが増えたからWorkspaceを増やす」だと、整理の都合と管理上の境界が混ざります。まず誰が管理するかを決め、その範囲の中でProjectへ分けます。

個人側にも複数の協力者がいるなら、個人だから必ず一つのWorkspaceでよいとは限りません。継続して管理する人、招待を決める人、作業内容を共有する相手を具体的に並べ、同じ管理単位へ置けるかを確認します。

## Public Projectとインターネット公開を分ける

Publicという名前も混同しやすいところです。Projectの公開範囲にあるPublicは、Workspaceのメンバーが見つけ、自分で参加できる設定として説明されています。Guestは明示的な招待が必要です。

なお、Project概要ページはWorkspaceメンバーのアクセスを広く記述する一方、ロールのページは内容へのアクセスにProject参加が必要と説明しています。細かな画面の見え方まで、二つの説明から同じだと断定しません。設計上は「一般メンバーが自分で参加できる範囲」と捉え、実際のロールで確認します。

インターネット向けには、別に[ProjectをPublishする機能](https://docs.plane.so/core-concepts/deploy)があります。こちらはサインアップせずに見られる公開ページを作るものです。

つまり、次の二つは別の設定です。

- 同じWorkspaceの誰がProjectへ参加・アクセスできるか。
- Workspace外の閲覧者へ公開ページを提供するか。

「外部向けのロードマップを出したい」という要望だけで、作業用Projectの全情報を公開対象へ含める必要はありません。公開する内容を選ぶ手順まで含めて設計します。この記事の調査ではPublishや権限変更を実行していません。

## 自分の管理者画面だけで確認を終えない

設定を見直すとき、管理者の自分がProjectを開けたことは、一般メンバーからの見え方の確認にはなりません。

導入先で検証するなら、機密情報を含まない確認用データを使い、Projectに参加していない一般メンバーと、Workspace管理者を分けて見ます。PrivateとPublicの各Projectについて、一覧で見つかるか、URLを直接開けるか、自分で参加できるかを記録します。

公開ページについては、Workspaceにログインしていないブラウザから確認します。Project内の参加権限を確かめるテストと、Publishしたページの閲覧を確かめるテストは分けます。この権限別の実機確認は今回実施していません。

Workspaceを分けても、同じアカウントの認証が別になることや、セルフホスト環境の基盤まで分離されることは、この設計からは言えません。ここで扱っているのはPlaneの管理単位です。インフラの分離や会社の認証方針は、それぞれの管理範囲で確認します。

分け方に迷ったら、「このWorkspaceを管理する人が、このProjectを開いてもよいか」を先に答えます。よければ、その中でProjectの公開範囲や参加者を決める。よくなければ、Workspace自体の所属を見直す。この順序なら、整理しやすさを優先して管理上の境界を曖昧にせずに済みます。
