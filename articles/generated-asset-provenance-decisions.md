AIで素材を生成すると、使わなかった候補も増えます。画像だけを保存しておくと、何を参考に生成したか、人が採用を決めたか、ゲームには加工後のどのファイルが入っているかを、後からたどりにくくなります。

素材ごとのIDを起点に、原本、生成条件、評価、実装での参照をつなぐと、この確認を分けて行えます。ここではVOLT NOMADの素材台帳を読み、記録できていることと、記録同士で状態が揃っていない箇所を調べます。

確認日は2026年9月11日、対象は`game-jam-lab`のコミット`f074703`です。生成APIを呼び直したり、新しい画像を作ったりはしていません。

## 出典の文書と、候補単位の台帳がある

リポジトリには、制作工程を説明する[ASSET_PROVENANCE.md](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/docs/ASSET_PROVENANCE.md)と、候補ごとの情報を持つ[review-manifest.json](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/tools/art-review/data/review-manifest.json)があります。

前者は、どの工程で生成や加工を使ったかを文章で説明します。後者は、生成バッチの中に候補を並べ、候補ごとに次の情報を持ちます。

| 記録 | 確認したいこと |
| --- | --- |
| `id`、`file` | 候補を識別し、原本へたどる |
| `prompt`、`model`、寸法、`seed` | 台帳に残っている生成条件を読む |
| `referenceFile`がある候補 | 参照画像へたどる |
| `generation` | 生成の状態、日時、利用量、エラーを読む |
| `codexReview` | 推奨や懸念の記録を読む |
| `humanReview` | 人の採否、評価、記録日時を読む |

この構造で、生成できたことと採用を決めたことを別の状態にできます。`seed`が`null`の候補もあるため、台帳があるだけで同一画像を再生成できるとは言えません。

## 一つの候補から、原本とゲーム用のファイルを追う

例として`final-fallen-machine-seraph-v9-c`を追います。台帳の関連部分だけを抜き出すと、次の値があります。

```json
{
  "id": "final-fallen-machine-seraph-v9-c",
  "model": "pixen",
  "seed": null,
  "file": "source/enemy/final-fallen-machine-seraph-v9-c.png",
  "codexReview": {
    "status": "recommended",
    "score": 98
  },
  "humanReview": {
    "status": "approved",
    "rating": 5
  }
}
```

実際のレコードには、生成日時、プロンプト、推奨理由、人のレビュー記録などもあります。ここでの98や5は台帳に保存された評価値であり、今回測定した画質や性能の値ではありません。

出典文書には、原本から背景を取り除いたcutoutをゲームで使う説明があります。[ゲーム側のコード](https://github.com/takahiro-saeki/game-jam-lab/blob/f074703848586828b6a5acc0e465ccdd2c0d5244/events/2026-ai-browser-game-jam-4/godot/games/charge_clicker/charge_clicker.gd)の`prime_current_form_3`は、`final-fallen-machine-seraph-v9-c-cutout.png`を`preload`しています。

つまり、台帳の`file`とゲームが読むファイルは異なります。固定コミットの原本とcutoutのSHA-256も計算し、バイト列が異なることを確認しました。ハッシュの違いだけで加工内容は分かりませんが、文書の説明とコードの参照を合わせて、原本と加工後ファイルの関係を追えます。

## 台帳を数えると、状態の違いが見える

[今回の確認スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/game-submission-evidence.mjs)は、固定コミットから台帳とファイル一覧を読みます。Node.js `v24.15.0`で確認した結果は次のとおりです。

- バッチは30件、候補は107件。
- 候補IDの重複はなく、107件すべての`file`がGitのツリーに存在した。
- `generation.status`は107件すべて`generated`だった。
- 人のレビュー状態は、`approved`が35件、`hold`が13件、`rejected`が3件、`unreviewed`が56件だった。

これは台帳と原本の所在の確認です。107枚を目視評価した結果でも、107枚すべてがゲームへ組み込まれているという意味でもありません。

さらに、撃破演出用の次の3候補は、`humanReview.status`が`unreviewed`のまま、ゲームコードから`preload`されていました。

```text
欠片: defeat-vfx-core-fracture-v12-a
光輪: defeat-vfx-voltage-halo-v12-b
破片群: defeat-vfx-machine-shards-v12-c
```

この結果から、台帳の`approved`一覧だけでは実装での参照一覧を作れない、と分かります。ただし、記録上未レビューであることから、人が一度も見ていないとまでは断定できません。確認できるのは、その時点の台帳に人の承認が記録されていないことと、コードに参照があることです。

## 採否と組み込み状態を、別に照合する

このリポジトリには、生成の状態、AI側の推奨、人の採否を分ける台帳がすでにあります。一方、各候補に「この実行用ファイルとして組み込まれた」と一律に記録する構造は、今回の台帳では確認できませんでした。

補うなら、候補のレビュー状態を無理に`approved`へ揃えるより、利用先を別の情報として持つ案が考えられます。

```text
候補ID
  ├ 原本のパスとハッシュ
  ├ 人の採否と判断理由
  └ 利用先
      ├ 加工後ファイルのパスとハッシュ
      ├ 加工方法を説明する文書またはスクリプト
      └ 参照を確認したコードのコミット
```

これは今後の設計案です。現在の素材台帳にこの構造を追加したわけではありません。

利用先が空なら「未使用」と即断するのではなく、まだ利用先を記録していない可能性も残します。コードを検索して得た参照も、その素材が通常のプレイ中に必ず表示される証拠にはなりません。今回実行したのは静的な参照確認で、ゲーム画面の再生確認は対象外です。

## 素材を差し替えるときの確認に使う

たとえば最終形態の画像を差し替えるなら、最初に候補IDと原本を特定し、採用理由を読み、加工後ファイルとコードの参照を追います。原本だけを上書きしても、ゲームがcutoutを参照していれば表示は変わらない可能性があります。

逆に加工後ファイルだけを差し替えると、原本との関係が説明できなくなることがあります。新しい候補として残すのか、同じ候補からの派生として残すのかを決め、その関係を記録します。

今回の調査では、候補IDから原本とレビューへたどれ、文書とコードを加えると加工後の利用先まで確認できました。同時に、人の承認状態とコードの参照が一致していない例も見つかっています。

台帳を一つの「採用済み」フラグに縮めず、生成、判断、利用を別々に記録する。素材を差し替えるときは、その記録から原本と利用先の関係を確かめます。
