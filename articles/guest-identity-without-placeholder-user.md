ログインせず日程へ回答した人に、後から回答を直してもらいたい。そこで名前を本人確認に使うと、同じ名前の人や、共有端末で別の人がログインした場合を扱えません。

SquadNoteの実装は、未ログインの人を仮のユーザー行へ入れる代わりに、回答一件を操作するためのトークンを発行しています。後からログインしたときも、自動的に名前で結び付けず、対象を確認してアカウントへ引き継ぎます。

本人の識別と、回答に対する操作権を分けて設計します。`circle-hub`の`9aec489`にある設計、移行SQL、API、端末保存を読み、2026年9月11日に関連テストを再実行しました。

## 団体の名簿を作る前に、回答の所有権を足す

[設計文書](https://github.com/takahiro-saeki/circle-hub/blob/9aec48963842dcaf16ce49c80317366509ab1b8f/docs/growth/09-guest-response-ownership.md)は、既存の`guest_attendance`へ操作権を追加する段階と、将来の団体単位の仮メンバーを分けています。

今回実装されたのは前者です。日程単位の回答へ所有権を付けることで、名前の一致を本人の証明として使わず、回答の一覧、変更、アカウントへの引き継ぎを扱います。

[移行SQL](https://github.com/takahiro-saeki/circle-hub/blob/9aec48963842dcaf16ce49c80317366509ab1b8f/apps/web/migrations/0007_add_guest_response_ownership.sql)には、主に次の列が追加されています。

| 列 | 用途 |
| --- | --- |
| `ownership_token_hash` | 未ログイン時の操作トークンを照合するハッシュ |
| `claimed_by_user_id` | 引き継ぎ先のユーザー |
| `claimed_at` | 引き継いだ時刻 |
| `attending_since` | 参加へ切り替わった時刻 |
| `updated_at` | 更新時刻 |

既存の回答には新しい所有トークンを後付けしていません。名前が同じという理由で過去回答を渡すこともありません。導入前の行を新機能へどこまで参加させるかが、データ移行の条件になります。

## 回答IDと操作トークンを別にする

回答IDは対象を探すために使います。それだけで編集できるわけではなく、回答時に渡した所有トークンの照合が必要です。

[トークンの実装](https://github.com/takahiro-saeki/circle-hub/blob/9aec48963842dcaf16ce49c80317366509ab1b8f/apps/web/src/server/api/lib/guest-response-ownership.ts)は、`crypto.getRandomValues()`で32バイトを作り、base64urlで43文字へ表現します。DBにはそのSHA-256だけを保存します。[Web Cryptoの仕様](https://www.w3.org/TR/webcrypto/#Crypto-method-getRandomValues)も、暗号学的に強い乱数を得るAPIとしてこのメソッドを定めています。

これは操作権を持つ文字列を作る方法であり、入力した名前の人物だと証明する方法ではありません。有効なトークンを持つ側が、その回答を操作できるというモデルです。

平文をDBへ保存しないことは、DB内のハッシュをそのまま操作鍵として再送されないための対策です。クライアントに残る元のトークンの保護まで不要になるわけではありません。

## 保存先を消すと、回答が消えなくても操作手段を失う

実装では回答IDとトークンをWebの`localStorage`、モバイルの`SecureStore`へ保存しています。URLには入れず、一覧や変更のAPIへ必要な参照を渡します。

Webの保存処理は壊れたJSONや形式の合わない行を除き、読取りに失敗したら空配列を返します。これは画面をクラッシュさせないための処理です。DBに回答がないことや、本人の回答を復元できたことを意味しません。

保存上限は100件です。端末の保存領域を消した場合、別端末を開いた場合、古い参照が上限から外れた場合に、名前から操作権を復元する実装はありません。別端末への自動同期も今回の対象外です。

また、[OWASPのlocalStorageに関する説明](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage)が示すように、JavaScriptから読み出せる保存領域にはXSSの影響があります。実装を紹介する際も、localStorageへ置いたので安全になったとは言えません。今回、XSS対策全体や実端末の保存領域を監査したわけではありません。

## 引き継ぐときは、ログインと確認を経て古い鍵を外す

ログイン後の画面は、端末に残る回答を対象として表示し、明示した引き継ぎ操作からAPIを呼びます。共有端末で別のアカウントがログインしただけで、自動的に結び付けないためです。

[引き継ぎAPI](https://github.com/takahiro-saeki/circle-hub/blob/9aec48963842dcaf16ce49c80317366509ab1b8f/apps/web/src/server/api/routers/attendance.ts)は、ログインしたユーザーとトークンの照合を経て、次の内容を更新します。

```ts
.set({
  claimedByUserId: ctx.session.user.id,
  claimedAt: new Date(),
  ownershipTokenHash: null,
})
```

ここは実装中の更新オブジェクトの抜粋です。前後に本人のセッション、既存の引き継ぎ先、トークンの確認があります。更新条件にも回答ID、引き継ぎ先が未設定であること、元のトークンハッシュを残しています。事前確認だけでなく、更新時の条件でも対象を絞るコードです。

成功したIDだけを端末の保存から削除し、以後はログインユーザーのIDで扱います。引き継ぎ済みの回答を別アカウントで上書きしないこと、旧トークンのハッシュを残さないことが、操作権の切替点です。

このAPIは複数回答を順に処理し、`claimedIds`と`rejectedIds`を返します。一覧全体を一括で成功とみなし、端末の参照を全部消す処理にはしません。一部が拒否された場合も、どの回答の操作権が移ったかを区別できます。

## 再実行した15テストの範囲

固定コミットの関連3ファイル、15テストが成功しました。Node.js `v24.15.0`、Vitest `4.1.4`で、元の作業ディレクトリを変更せず、一時コピーから実行しています。

| 対象 | 確認した内容 |
| --- | --- |
| トークン関数 | 発行形式、異なる生成値、正しいハッシュの照合 |
| 回答API | 誤ったトークンの拒否、正しい参照、公開結果から所有情報を除外 |
| 公開状態 | 非公開へ戻した日程を端末保存の一覧へ返さない |
| 引き継ぎ | 別ユーザーへの再引き継ぎ拒否、成功時のハッシュ削除、競合後に更新成功としない分岐 |
| Web保存 | 壊れたデータ、同じ回答IDの更新、成功したIDだけの削除 |

トークン関数は実際の乱数・ハッシュAPIを使います。一方、回答APIのテストは実ルーターを呼びますが、DBや通知はモックです。SQL条件の評価や複数プロセスでの競合を、実D1で再現した試験ではありません。

[実行スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/batch05-circle-tests.py)と[結果](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/production/2026-09/batch-05/guest-tests.json)に確認範囲を残しました。モバイルのSecureStore実機試験や、引き継ぎ画面の操作は今回実施していません。

## 人の同一性を、回答の操作権から推測しない

この設計で実装済みなのは、回答単位の操作トークン、同じ端末からの管理、確認後のアカウントへの引き継ぎです。団体の仮名簿、名前からの過去回答の自動取得、別端末同期は将来の別機能として残っています。

ゲストの便利さを広げるときは、何を持っていれば何を操作できるかを先に書きます。回答を編集できることから、同じ名前の別回答や団体の名簿まで本人のものだと広げないことで、次に必要な本人確認も見えてきます。
