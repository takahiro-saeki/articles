Planeで作業を管理していても、コードはGitHubのPRでレビューします。そこで同じ作業のGitHub Issueも作ると、説明、担当者、完了状態を二か所で更新することになります。

同じ情報をどこで編集するかを、先に決めます。Planeに実行タスクがあり、GitHub側でIssueを受け付ける理由がなければ、まずWork ItemとPRを結びます。Issueをもう一つ作ることを、連携の前提にしません。

以下は2026年9月11日に確認した公式ドキュメントをもとにした運用設計です。実環境で同期を有効にした記録や、二重管理を解消できたという実測報告ではありません。

## 同じ作業に見えても、置きたい情報は違う

たとえば「体験参加者の権限を制限する」という作業なら、Planeには目的と受け入れ条件、PRには変更したコードと検証結果を置けます。

| 情報 | 主に編集する場所 | 他方に残すもの |
| --- | --- | --- |
| なぜ変更するか、何を満たせば完了か | Plane Work Item | PRからの参照 |
| どのコードをどう変えたか | GitHub PR | Work Itemからの参照 |
| 利用者が報告した再現手順 | 受付に使うGitHub Issue | Planeからの参照と対応方針 |
| リリース後の確認作業 | Plane Work Item | 対象PRやリリースへの参照 |

これは推奨する配置例です。すべてのプロジェクトにGitHub Issueが必要だという意味ではありません。

外部から不具合報告を受けるリポジトリなら、報告者が議論できるIssueを残す理由があります。そのIssueの全文を、社内向けの優先度や実装計画と一緒にもう一度編集し始めると、二つの説明が別々に育ちます。元の報告はリンクで参照し、対応の判断を書く場所を決めます。

## 自動同期は、編集場所を決めた後に検討する

[PlaneのGitHub連携仕様](https://docs.plane.so/integrations/github)は、確認時点でProとして案内されています。Issue同期には方向の設定があり、一方向はGitHubからPlaneへ流れ、Plane側の内容を上書きします。双方向なら両側の変更を同期します。

この仕様から、一方向同期のPlane説明欄に独自の受け入れ条件を書き足す運用は避けたい、と判断できます。同期元がその文章を持っていなければ、次の更新で維持される前提にできません。

ここでは、自動同期を使う場合も次のように編集ルールを一つ決めます。

```text
GitHubを受付に使う場合の運用案

報告の再現手順: GitHub Issueで更新
実装の受け入れ条件: 別のPlane Work Itemで更新
両者の関係: 相互リンク
同期する説明欄: 独自の別文書を追記しない
```

「別のWork Item」は、同じ文章を手で複製する意味ではありません。報告への対処に複数の実装やリリース作業が必要なとき、それぞれの完了条件を持つタスクへ分ける案です。単純な修正で一つのIssueにすべて収まるなら、Plane側の独立した説明を増やさずに済む場合もあります。

双方向同期なら、どちらで編集してもよい設計にできます。ただし、受付用の文章と実装用の文章を同じ欄に混ぜる問題は残ります。同期の方向を変えるだけで、文章の読者や用途まで整理されるわけではありません。

## PRへの参照と、状態変更を分けて選ぶ

同じ公式ページでは、PRのタイトルまたは本文にPlaneのIDを書く方法が説明されています。設定済みの連携では、`WEB-344`は参照のみ、`[WEB-344]`は設定したPRイベントに応じた状態変更も行います。次は公式の例示IDを使ったPR本文の例です。

```text
Related work: WEB-344
```

この表記でまず参照をつなぎ、状態は作業の受け入れ条件を見て更新する、という運用を選べます。状態の自動変更まで使うなら、設定したイベントとの対応を確認して角括弧付きにします。

```text
Related work: [WEB-344]
```

文字列を書くだけで未設定の連携が動くわけではありません。ここで二つの形式を区別しているのは、単にPRを関連付けたい場合と、PRのイベントをタスクの状態へ反映したい場合で、意図が違うからです。

たとえばマージ後にデータ移行、配布、本番確認が残る作業では、PRのマージをタスク全体のDoneへ直結させると早すぎます。導入案としては、マージを「実装済み」へ対応させるか、自動変更を使わず残りの受け入れ条件を確認します。逆に、コードのマージが完了条件である小さな修正なら、Doneへの対応が合う場合もあります。

## GitHubのIssueを閉じる構文とは別に扱う

GitHub自身にもPRとIssueの連携があります。[GitHubの公式説明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)では、PRの説明に終了キーワードを使ったリンクは、PRがデフォルトブランチを対象にするときに解釈され、そこへのマージによってIssueが閉じます。

たとえば次はGitHub Issueに対する構文の例です。

```text
Closes #123
```

これはPlaneのWork Itemを閉じる指示ではありません。数字だけのGitHub Issue番号と、PlaneのProject識別子付きIDを、同じ仕組みの別表記として扱わないようにします。

また、PRが閉じたという事実だけでは、マージされたか、マージせず閉じたかは分かりません。タスクの受け入れ条件が成立したかを見たいなら、イベントの名前と、そのイベントを完了とみなす理由を対応させます。

## 導入時に確かめたいのは、更新の行き先

今回確認できたのは、公式仕様上の同期方向、参照形式、終了キーワードの条件です。実際の同期遅延、同時編集の競合、個人環境の連携設定は検証していません。

導入先で試す場合は、実作業から離した確認用のIssueとWork Itemで、タイトル・説明・状態をそれぞれ片側から変更し、どこへ反映されたかを記録します。参照のみのPRで状態が変わらないことと、状態変更用のPRで設定した遷移が起きることも分けて見ます。

その確認に入る前に、「報告の修正はここ」「実装の完了条件はここ」と説明できる配置を作っておくと、同期結果が意図どおりかを判断できます。同じ文章を二か所に置く必要がなければ、参照だけで足りる範囲から始められます。
