予約表に38行あることと、38日間予定どおり公開できたことは同じではありません。日本語原稿だけ公開されている日、英語版の投稿に失敗した日、再実行で復旧した日があっても、予約表の行数は変わらないためです。

このリポジトリには、2026年8月3日から9月9日までの日次予約が残っています。最初は「38日間、Qiita・Zenn・dev.toへ毎日投稿」という記事候補でしたが、データが表す内容を確認してタイトルを変えました。

日本語はQiitaとZennのどちらか一方へ出し、その記事の英訳をdev.toへ出す構成です。3媒体それぞれに38本ではありません。投稿数を報告する前に、予定、日本語の公開記録、英語の公開記録を分けて照合します。

## 調査する時点を固定する

対象は`articles`のコミット`8a1bfa8`です。調査日は2026年9月11日。予約表、日英のfrontmatter、Git履歴、GitHub Actionsの実行記録を確認しました。

集計はNode.js `v24.15.0`で実行し、対象コミットから`git show`でファイルを読みました。いまの作業ディレクトリへ原稿を追加しても、過去の集計対象が変わらないようにしています。

```bash
node experiments/article-stock-2026-09/audit-publishing.mjs 8a1bfa8
```

[集計スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/audit-publishing.mjs)は、対象コミットの予約表から日本語と英語のパスを取り出します。本文の閲覧数や評価を取得する処理はありません。

## 予約表の38件を、日付と媒体へ分解する

集計した結果は次のとおりです。

| 項目 | 結果 |
| --- | ---: |
| 予約表の行数 | 38 |
| 重複を除いた予約日 | 38日 |
| 最初と最後の日を含む期間 | 38日 |
| 日本語がZennの行 | 19 |
| 日本語がQiitaの行 | 19 |
| 日本語に公開済み記録がある行 | 38 |
| 英語に公開済みフラグと投稿IDがある行 | 38 |
| 英語のcanonicalが日本語の対応先と一致する行 | 38 |

最初は2026年8月3日、最後は9月9日です。期間の日数とユニークな日付数が一致するので、この予約表には一日一件ずつ、日付の抜けなく予定が入っています。

ここで確認したのは、38組、計76原稿の公開済み記録です。日本語38本の内訳が19本ずつであり、38本をQiitaとZennの両方へ重ねて出した構成ではありません。

## 公開済みの判定を媒体ごとに決める

予約表だけでは投稿の完了は分かりません。日本語と英語のファイルを開き、現在の投稿スクリプトに合わせて判定します。

Zennは`published: true`を記録上の公開済みとします。Qiitaは`ignorePublish: false`に加え、`id`が空でも`null`でもないことを見ます。英語版は`published: true`と`devto_id`の両方です。

```text
予約日
  ├─ 日本語パス → 媒体に対応した公開済み判定
  └─ 英語パス   → publishedとdevto_idの確認
                   canonicalを日本語の対応先と照合
```

既存の投稿スクリプトはfrontmatterを行単位で読みます。今回の過去記録の集計もその読み方に合わせています。これは全ファイルが正しいYAMLであることを保証する検証ではありません。新規原稿のYAML検証は、別に行います。

Zennのcanonicalは、投稿アカウントとslugから決まるURLを照合しました。Qiitaは日本語ファイルの投稿IDを使い、`https://qiita.com/hiro123/items/<id>`と一致するかを確認しています。タイトルが似ていることだけでは同じ記事と判定しません。

## workflowが成功した回数は、公開した本数ではない

このリポジトリの予約workflowには、定期起動に加えて手動実行があります。公開済み判定で何もせず正常終了する場合もあるため、成功したrunを数えても投稿数にはなりません。

実際、2026年8月4日の手動実行には、dev.toがタグを理由に422を返した記録があります。ログには`react native`などの空白を含むタグが拒否されたことが残っており、その後のコミットでタグの正規化が入っています。

参照: [失敗したrun](https://github.com/takahiro-saeki/articles/actions/runs/30867501704)、[タグを正規化した変更](https://github.com/takahiro-saeki/articles/commit/161138c)

9月11日時点のfrontmatterは、この失敗後に回復した状態を含みます。「最終的に公開済みになっている」と「初回実行が成功した」を分けないと、障害がなかったような集計になります。

また、定期実行が指定時刻どおり始まる保証も置けません。GitHubの[公式ドキュメント](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)では、高負荷時の遅延やジョブが落とされる可能性が説明されています。毎朝同じ時刻という運用目標と、実際の公開時刻の評価は別に必要です。

## この集計だけでは言えないこと

今回の38件一致から、次の結果までは導けません。

- 毎日09:00ちょうどに読者が記事へアクセスできたこと。
- 38日すべてで手動復旧が不要だったこと。
- 投稿頻度によって閲覧数やフォロワーが増えたこと。
- 現在も全媒体の公開ページが正常に表示されること。

frontmatterのIDは投稿結果を保存した記録です。公開APIの`published_at`や現時点のページ表示を全件照合したものではありません。正確な公開時刻を集計する場合には、予約日とは別に、媒体側が返す公開日時を取得して比較する必要があります。

同様に、`updated_at`は更新日時なので、それを最初の公開時刻として使いません。記事修正や再実行が入れば、日付の意味が変わります。

## 次のストックでも、照合する単位は一組

この監査で使った単位は、日本語一本と英語一本です。予約表、日本語パス、英語パス、canonicalの関係を一行ずつ追うと、片方だけ欠けている状態を見つけられます。

次の制作では、原稿を完成させることと予約表へ入れることも分けます。完成した下書きはまだ公開済み件数へ加えず、日英の両方が揃ったストックとして管理します。

今回の結果を正確に書くなら、「38日分の予約があり、その38組すべてに日英の公開済み記録が残り、canonicalも一致した」です。予定どおりの公開時刻や読者の反応は、その次に別のデータで確かめる問いとして残ります。
