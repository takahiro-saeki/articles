AIから差分とテストを受け取り、テストがすべて通った。そこで困るのは、そのテストが何を守っているかを、自分の言葉で説明できないときです。

レビューで試したいのは、守るべき条件を一つ選び、その条件を壊したコードでテストが失敗するか確かめる方法です。失敗した期待値から、実装のどの条件を守っているかを追えます。

この記事では、SquadNoteの実際の通知ルーターと既存テストを作業用コピーに取り出し、削除条件を一つ外しました。元のコードでは8件成功、変更後は7件成功・1件失敗でした。確認日は2026年9月11日、Node.js `v24.15.0`、Vitest `4.1.4`です。

題材のコードを誰が書いたかは、この検証では判定していません。AIから受け取ったコードにも使えるレビュー手順として示します。継続運用の効果を報告する体験記ではなく、今回試した確認手順です。

## 「ログアウトできる」を、残るデータの条件に直す

題材は、端末のPushトークンを削除する処理です。同じ端末でアカウントAからBに切り替わった後、遅れてAの解除要求が届く場合を考えます。

「ログアウトできる」では、成功の意味が広すぎます。ここで守りたい条件は次の一つです。

> Bへ移った端末のトークンを、以前の所有者Aの要求で削除しない。

この条件には、操作する人、操作する対象、操作後に残るものが含まれています。「認可を適切にする」と書くより、テストへ移しやすくなります。

実装の削除条件は、関連部分を抜き出すと次の形です。

```ts
and(
  eq(pushTokens.userId, ctx.session.user.id),
  eq(pushTokens.token, input.token),
)
```

トークン文字列が一致することに加え、現在のセッションのユーザーが所有していることを条件にしています。登録時の所有者変更も含めた全体の動作は別の論点なので、今回はこの削除条件を読む範囲に留めます。

## 先に反例を並べ、既存テストと照合する

コードを変更する前に、反例の操作順を書きます。

1. Aが`ios-1`と`android-1`を登録する。
2. Bが`android-1`を登録し、そのトークンの所有者がBへ移る。
3. Aが`android-1`の解除を要求する。
4. Bの`android-1`とAの`ios-1`が残ることを確認する。

[既存のテスト](https://github.com/takahiro-saeki/circle-hub/blob/0cda1e865ad80d1529197729d8d436e96d56edc7/apps/web/src/security/push-token-privacy.test.ts)には、この順序がすでにあります。APIを呼んだかだけでなく、最後にDBから行を読み直しています。説明用に短くすると、期待値はこうなります。

```ts
expect(await rows()).toEqual([
  { user_id: "user-b", token: "android-1", platform: "android" },
  { user_id: "user-a", token: "ios-1", platform: "ios" },
]);
```

`rows()`がどこを読むかも確認します。今回は実ルーターとlibSQLのテスト用DBを使い、外部HTTPをモックする構成でした。`unregisterPushToken`そのものを成功するモックへ置き換えていたら、この削除条件を調べるテストにはなりません。

## ユーザー条件だけ外すと、何が落ちるか

実験ではコミット`0cda1e8`を一時ディレクトリへ展開し、元のテストを実行しました。その後、作業用コピーだけで上の条件を次の形に変えます。

```ts
eq(pushTokens.token, input.token)
```

これは採用する修正ではなく、テストを調べるための故障です。トークンだけで削除すれば、古い所有者Aの要求でもBの登録が消えるはずです。

| コード | 成功 | 失敗 | 確認したこと |
| --- | ---: | ---: | --- |
| 元の削除条件 | 8 | 0 | 既存の期待値を満たす |
| ユーザー条件を削除 | 7 | 1 | アカウント移管後の解除を検出する |

失敗したのは「アカウント切替はその端末だけ移管し、旧ユーザーは削除できない」というテストでした。DBの行に対する期待値が一致しなくなっています。

故障前から失敗しているテストでは差を判断できません。また、故障後に構文エラーで起動しなくなっただけでは、狙った条件を検出したことになりません。今回はテストの期待値が失敗したことまで確認しました。

[実験スクリプト](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/mutation-check.mjs)は、元のリポジトリを変更せず、固定コミットの展開、正常系の実行、条件の削除、再実行を行います。対象リポジトリの依存パッケージがインストール済みなら、記事リポジトリから次のように実行できます。

```bash
node experiments/article-stock-2026-09/mutation-check.mjs ../circle-hub-multi-device-push
```

## テストが落ちなかった場合に読むところ

今回の反例は検出できました。別の差分で故障後も通るなら、すぐにテスト件数を増やす前に、反例が対象コードへ届いているか確認します。

たとえば、ログインユーザーが常にAのモックになっていれば、Bへの移管は成立しません。削除後に行を読み直さず、レスポンスが成功かだけを見ていれば、余計な削除を見逃せます。変更したコードを通らない別ルーターをテストしている場合もあります。

読む順序は、入力の作り方、実行する関数、外部との境界に置いたモック、最後の期待値です。どこまで本物が動くかを把握してから、足りない反例を追加します。

この方法で分かるのは、選んだ故障を選んだテストが検出することです。すべての認可漏れ、並行実行の順序、通知の実端末への到達までは証明しません。今回も外部配信や実機を使っていません。

AIに追加説明を求めるなら、「安全ですか」よりも、「この条件を外すと、どのデータが消え、どの期待値が失敗するか」を聞くと、説明を実行結果と照合できます。レビュー記録には、守る条件、使った反例、実際に失敗した期待値を残します。その記録があれば、次に同じ条件を整理するときも、削ってよいかを判断できます。
