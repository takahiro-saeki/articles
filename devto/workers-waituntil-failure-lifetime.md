Passing a Promise to waitUntil and returning 202 does not report the success of the background work. Record when the response has been consumed separately from when the work completes or fails.

This comparison used local workerd, paused a substitute dependency, and released it with success or failure after the response. The checks record both response consumption and the later job result for each use of waitUntil.

## Work awaited before a response and work that continues afterward

The verification date was September 11, 2026. The environment was macOS 26.6.2, Node.js 24.15.0, Wrangler 4.131.0, Miniflare 5.20260910.0-alpha, and workerd 1.20260910.1, with compatibility_date 2026-09-11 and nodejs_compat enabled. That Miniflare version is also a dependency of this Wrangler release.

The example project, circle-hub, has a runAfterResponse helper in its [notification implementation](https://github.com/takahiro-saeki/circle-hub/blob/a34608c611ded6549c1176a7977e68e1bc62a8db/apps/web/src/server/api/lib/notify.ts) at fixed commit `a34608c`. It passes a Promise to ctx.waitUntil. This investigation did not modify the production implementation or send actual notifications.

The comparison Worker used the following job. SINK is a Node-side substitute Service Binding, not a real service. Its gate response stays pending until the test releases it with 200 or 503. Env was generated by Wrangler.

```ts
async function backgroundJob(env: Env, id: string) {
  const response = await env.SINK.fetch(`http://sink/gate/${id}`);
  if (!response.ok) throw new Error(`Background job failed: ${id}`);
  await response.text();
  await env.SINK.fetch(`http://sink/done/${id}`);
}
```

One case awaited this function. Another passed its Promise to ctx.waitUntil and immediately returned 202. The test attempted to consume the response body before releasing the pending dependency.

The [comparison Worker and harness](https://github.com/takahiro-saeki/articles/tree/codex/article-stock-2026-09/experiments/article-stock-2026-09/workers-batch15) include a lockfile with pinned dependencies. After installing them, run `node experiments/article-stock-2026-09/workers-batch15/run.mjs` from the repository root. The local server stays running for the cache comparison after the checks finish; stop it with Ctrl+C when done.

| Condition | While the dependency stayed pending | After releasing it successfully |
| --- | --- | --- |
| await backgroundJob | The response body was not yet available | Completion was recorded before 202 was consumed |
| Pass the Promise to ctx.waitUntil | 202 and its body were consumed first | Completion was recorded afterward |

waitUntil is not an API that postpones starting the work until after the response. Calling backgroundJob starts the operation. In this trace, job startup preceded response consumption.

## Does one rejection stop a separate Promise?

The next request passed 2 Promises to separate ctx.waitUntil calls. One dependency received 503 first; the other received 200 later.

The original response remained 202, and the successful job recorded completion. The failed job did not complete and had 1 start recorded at the observation point. This corresponds to the independence of separate waitUntil Promises described by the [official Context specification](https://developers.cloudflare.com/workers/runtime-apis/context/).

This was not a comparison with combining them into a single Promise.all. Observing only 1 start also does not establish that another platform or caller has no retry behavior. The observation covers this Worker and its local records.

## Record failures separately from the 202 response

The explicit failure-observation case used this caller. It is a branch in the comparison Worker, not a change already applied to the original app.

```ts
ctx.waitUntil(backgroundJob(env, id).catch(async error => {
  console.error(JSON.stringify({ event: 'background-failed', id, message: error.message }));
  await env.SINK.fetch(`http://sink/failed/${id}`);
}));
```

Releasing the dependency with 503 after consuming 202 produced a failure log and a failure record at SINK. The start count was again 1. The catch block records the failure without retrying the job.

Logging an error and returning normally from catch resolves the outer Promise. That resolution is different from successful completion of the original work. Use distinct completion and failure events, with enough identity to connect them to the operation.

Writing the failure record is itself another I/O operation. Its delivery guarantee was not tested here. An actual observability integration also needs checks of the collection path and its behavior when records are lost.

## A local job lasting 35 seconds does not establish its production lifetime

Another case held the substitute dependency for 35000 milliseconds after the 202 response had been consumed. In this local workerd environment, completion was recorded after the gate was released.

The official HTTP-triggered waitUntil behavior has a limit of up to 30 seconds after the response is sent or the client disconnects. Calls within the same request share that allowance; it is distinct from the total elapsed time of the request.

The 35-second local case therefore did not reproduce the production limit. Its completion cannot justify expecting the same lifetime on Cloudflare. This investigation did not deploy to production or test client disconnection.

## Work that needs retries requires a storage and delivery design

waitUntil receives a running Promise. Do not treat that call as also providing durable storage for the job, later retrieval, or automatic redelivery after failure.

The [Cloudflare Queues retry specification](https://developers.cloudflare.com/queues/configuration/batching-retries/) describes redelivery, maximum retries, and dead-letter queues. Work that must continue after failure needs such a delivery path and a policy for duplicate execution. This article did not install a Queue, publish messages, or test a consumer.

The experiment recorded 4 events: response, start, completion, and failure. Begin verification by connecting the later result to the response, instead of counting a 202 alone as successful work.
