## canonicalが未確定の49組

[canonical-pending.json](canonical-pending.json)に、ID・タイトル・slug・日英pathを全件保存した。今の原稿を壊さず、URLが確定したときに対応付けられる一覧である。これは予約表や投稿指示ではなく、外部APIを呼ぶ処理も持たない。

2026-09-12に[Qiita APIの作成仕様](https://qiita.com/api/v2/docs#post-apiv2items)を再確認した。作成要求には任意のitem IDや公開URLを指定する項目がなく、作成応答にidとurlが含まれる。今回の記事はQiita上で作成しておらず、slugだけから将来のitem IDを求める根拠はない。架空のIDや、Qiita記事ではないGitHubのURLで埋めることはしていない。

[Foremの作成仕様](https://developers.forem.com/api/v1#tag/articles/operation/createArticle)はcanonical_urlにnullを許容するが、それだけで依頼の「日本語版の公開予定URLにする」という条件を満たしたことにはならない。既存の単体投稿スクリプトがYAMLのnullを文字列として読む挙動もバッチ12で確認済みであり、APIへ送って動作確認する手順は今回実行しない。

現時点の選択にはユーザーの判断が必要となる。ローカル下書きの完成条件としてcanonical未確定を認め、公開時に正しいURLを入れる運用へ変更するか、対応する公開予定URLが確定するまで49組を未完成として保つか。回答前に完成数を増やしたり、Qiitaへ記事を作ったりはしない。

## 再照合の入口

```sh
python3 scripts/audit-article-stock-completion.py
node scripts/validate-article-stock.mjs --all --allow-pending-canonical
node scripts/validate-article-stock.mjs --all
```

承認前の最後のコマンドは、未確定canonicalにより失敗した。承認後の現行validatorは承認済み方針と予約表も確認し、nullを認める。保存済みの失敗結果は当時の記録である。この失敗を無視して完成とする処理は入れていない。--allと--batchを同時に指定する使い方も拒否し、誤って一部だけを検証することを防いでいる。

各バッチの保存済み検証は、そのバッチ時点の記録である。後の原稿推敲を理由に、当時の測定値や実行日を上書きしない。
