新しい個人開発の準備をテンプレート化するとき、前のProjectの識別子、期限、担当者まで無条件に使い回さないようにします。共通にするのは開始時の確認手順で、対象のリポジトリや配布経路は新しいProjectごとに決めます。

ここではPlaneのProject Templatesの公式資料を確認し、3つの初期タスクを含むローカルの設定案を作りました。Plane上のテンプレート保存や新規Projectの作成はしていません。

## Project全体を用意するテンプレートを選ぶ

[Project Templatesの公式説明](https://docs.plane.so/templates/project-templates)にはBusinessの表示があります。Projectのプロパティに加え、States、Labels、Work item types、初期Work Itemを用意できると説明されています。作成場所はWorkspace SettingsのTemplatesです。

一枚の作業の説明や子作業を使い回す[Work Item Templates](https://docs.plane.so/templates/work-item-templates)とは、再利用する範囲が違います。すでに存在するProjectへタスクを追加したいだけなら、Project全体を作り直す必要はありません。

今回の題材は、新しいProjectを始めるときに、最初の確認を空欄のまま忘れないための案です。既存Projectの複製による移行事例ではありません。

## 共通の初期タスクは3つに絞る

最初から開発工程の全チケットを並べると、まだ採用していない配布経路まで既定になります。次の3つは、そのProjectの条件を決めるための作業として用意しました。

| 初期タスク | 残す結果 |
| --- | --- |
| 対象と管理先を確認する | プロダクト、リポジトリ、担当、参照先 |
| 最初に渡す成果物を決める | 配布経路と初回の範囲 |
| 初回確認の手順を用意する | 実行条件、期待結果、記録先 |

対象、配布、検証という開始時の判断を残すために分けました。「3つが最適」と計測したわけではありません。

たとえば「初回確認」の完了は、何かを試したという報告だけではなく、どの入力を使い、何が見えればよいかを文書にした時点です。実際の製品確認の結果とは分けます。まだ作っていない機能のテストが通ったことにしません。

## 毎回の判断まで固定しない

| 項目 | テンプレート側の役割 | 新規Projectでの確認 |
| --- | --- | --- |
| 名前と識別子 | 命名時の説明を置く | 実際の製品名、既存との衝突 |
| リポジトリ | 記載欄を用意する | 対象URL、owner、作業場所 |
| 担当と閲覧範囲 | 設定方針を説明する | 誰が進め、誰が見られるか |
| 日付 | 決めるタイミングを説明する | このProjectで実行可能な日程 |
| 状態とラベル | 意味の定義を揃える | 新しいProject内の値と対応 |
| 配布経路 | 初期タスクで選ばせる | Web、ストア、ゲーム配布などの対象 |

同じラベル名を使うことと、別ProjectのIDを流用することは別です。[Work Item Labels](https://docs.plane.so/core-concepts/issues/labels)はProject単位の設定です。後からAPIで作業を追加する場合も、表示名だけから以前のIDを再利用する設計にはしません。

前のProjectにあった具体的な期限や担当者が、次のProjectにも妥当かは個別に確認します。設定を保存できたことと、値が新しい用途に合っていることを分けて扱います。

## 二つの架空Projectへ当てはめてみる

ローカルの設定案を、Web LabとGame Labという二つの架空Projectへ当てはめました。実在するPlane Projectや新規リポジトリを作ったわけではありません。

| 確認項目 | Web Lab | Game Lab |
| --- | --- | --- |
| 識別子の案 | WEBLAB | GAMELAB |
| 最初の成果物 | Webプレビュー | ブラウザー向けゲーム一式 |
| 初回確認 | URLと主要導線 | 起動と操作 |
| 共通の初期タスク | 対象・配布・検証の3件 | 対象・配布・検証の3件 |

共通の確認項目は残せましたが、配布と検証の中身は変わりました。ゲーム側へWebサービスのログイン確認を無条件に入れたり、Web側へゲームパッド確認を必須にしたりする必要はありません。

これは設定案の机上確認です。Planeが初期タスクを生成した結果ではなく、作成時間の短縮も測っていません。具体的な値を未決定のまま残す項目があるため、このJSONをそのままAPIへ送る形式にもしていません。

## 保存後に確かめるものを用意してから導入する

公式手順では、Project作成時にテンプレートを選び、設定を調整してからCreateします。ここで識別子、担当、閲覧範囲、日付を読み直す工程を入れる案です。

作成後は、初期タスクが期待した件数と説明で入っているか、状態やラベルが新しいProjectの設定に対応しているか、過去の期限や参照先が混ざっていないかを確認します。既存Projectまでテンプレートの変更が反映される、という動作は今回確認していません。

この調査では、テンプレート一覧APIの応答に内容がありませんでした。空の応答だけではテンプレート0件とは判断せず、既存登録数は未確認としています。機能を利用できる契約・権限と実際の画面は、導入時に確認する対象です。

2026年9月11日に公式資料を確認し、[3タスクと2つの適用例](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/production/2026-09/batch-11/proposed-configurations.json)をローカルへ保存しました。この案では初回の確認手順を共通にし、Projectごとの値は作成時に決めます。
