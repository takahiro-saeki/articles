音に反応するダッシュボードでは、全体の大きさに反応させたいのか、特定の周波数帯へ反応させたいのかで、読む値が変わります。RMSと周波数のバイト値を同じ「音量」として扱うと、動きの調整が合わなくなります。

個人開発のbeautiful-dashboard-for-bgaにある解析処理を読み、合成音で確かめました。振幅を2倍にするとRMSは2倍になりましたが、周波数の最大バイト値は211から232への変化でした。動きを同じ比率で変えたいときは、値の尺度も揃えます。

## まず、動いているのがモックか入力音かを分ける

対象は[リポジトリの固定commit](https://github.com/takahiro-saeki/beautiful-dashboard-for-bga/tree/6f69cac1fe792436fced3a5215633e850262db59)です。lockfile上の版はReact 19.2.4、Vite 7.3.1、TypeScript 5.9.3でした。

[useAudioEngine](https://github.com/takahiro-saeki/beautiful-dashboard-for-bga/blob/6f69cac1fe792436fced3a5215633e850262db59/src/hooks/useAudioEngine.ts)は初期状態でisMockがtrueです。合成波形や変動する周波数配列を作り、音声入力がなくても描画用データを更新します。MICやファイル入力を開始すると実入力へ切り替え、stopではモックへ戻ります。

つまり、画面が動いていることだけでは、マイク入力を取得できたとは判断できません。今回の検証でもマイクは使っていません。解析関数はNode.js、Web Audio部分はローカルページを開いたHeadlessChrome 152のOfflineAudioContextで確認しました。確認日は2026年9月11日です。

## 時間波形と周波数は、別のAnalyserNodeで読む

取得したコードには、時間波形用と周波数用のAnalyserNodeがあります。

| 用途 | fftSize | 使用する値 |
| --- | ---: | --- |
| 時間波形 | 4096 | getFloatTimeDomainDataで読む波形、RMS、peak |
| 周波数 | 2048 | getByteFrequencyDataで読む配列、帯域別の値 |

周波数用のfrequencyBinCountは1024です。[Web Audio仕様](https://www.w3.org/TR/webaudio/#AnalyserNode)では、これはfftSizeの半分です。周波数のバイト値はデシベル値をminDecibelsとmaxDecibelsの範囲から0〜255へ変換した値で、波形の振幅そのものではありません。

[AudioAnalysis.ts](https://github.com/takahiro-saeki/beautiful-dashboard-for-bga/blob/6f69cac1fe792436fced3a5215633e850262db59/src/audio/AudioAnalysis.ts)のRMS計算は次の関数です。型以外は元の計算を保っています。

```js
function computeAmplitude(timeDomain) {
  let sum = 0;
  for (let i = 0; i < timeDomain.length; i++) {
    const v = timeDomain[i];
    sum += v * v;
  }
  return Math.sqrt(sum / timeDomain.length);
}
```

各サンプルを二乗して平均し、その平方根を取ります。瞬間的な最大値を返すpeakとは違います。この実装には空配列の特別扱いがなく、空配列ではNaNになりました。実入力側はfftSize分の配列を作るため、今回のブラウザ試験では空配列を渡していません。

## 合成音で、尺度の違いを確認する

ブラウザ試験では468.75 Hzの正弦波を作りました。OfflineAudioContextの一時停止に0.5秒を指定し、停止後に時間波形と周波数を読み、同じ解析関数へ渡しています。オフライン処理なのでスピーカーからは鳴らしていません。

解析器のfftSizeとsmoothingTimeConstantは実装に合わせ、時間波形側を4096と0.8、周波数側を2048と0.85にしました。入力元はアプリのマイクやファイルではなく、試験用OscillatorNodeです。

| sampleRate | 入力の振幅 | RMS | 最大周波数ビン | 最大バイト値 |
| --- | ---: | ---: | ---: | ---: |
| 48000 | 0 | 0 | 対象なし | 0 |
| 48000 | 0.25 | 0.176777 | 20 | 211 |
| 48000 | 0.5 | 0.353553 | 20 | 232 |
| 44100 | 0.5 | 0.353600 | 22 | 232 |

RMSは小数点以下6桁へ丸めています。最大ビンはgetFloatFrequencyDataの結果から選び、バイト値の上限への張り付きだけで位置を判定しないようにしました。

48000の2条件では、入力の振幅とRMSの比が対応しました。一方、最大バイト値は同じ割合にはなりませんでした。デシベルから変換される値なので、バイト値の平均を「波形の平均振幅」とは呼べません。

この値は、指定したグラフで一時停止後に周波数を初めて読み取った結果です。平滑化には過去の解析値が関係するため、読み取り回数や設定が違う画面で、211や232が常に出るという主張ではありません。

## 固定ビンの「低音」はsampleRateで変わる

この実装のextractBandsは、周波数の配列を固定の添字範囲へ分け、バイト値の平均を255で割ります。周波数の単位で範囲を指定しているわけではありません。

```js
function binHz(index, sampleRate, fftSize) {
  return index * sampleRate / fftSize;
}
console.log(binHz(20, 48000, 2048)); // 468.75
console.log(binHz(22, 44100, 2048)); // 473.73046875
```

同じ468.75 Hzの入力でも、試験では48000のときビン20、44100のときビン22が最大でした。ビンの周波数間隔が違い、入力周波数とビン中心が常に一致するとは限らないためです。

元コードの固定範囲を、sampleRateが48000の場合の境界へ換算すると次のようになります。上端のビン番号は含みません。音響用の厳密な帯域定義ではなく、このコードの配列区分です。

| 名前 | ビン範囲 | 換算した境界 Hz |
| --- | --- | --- |
| subBass | 0以上4未満 | 0〜93.75 |
| bass | 4以上12未満 | 93.75〜281.25 |
| lowMid | 12以上40未満 | 281.25〜937.5 |
| mid | 40以上100未満 | 937.5〜2343.75 |
| highMid | 100以上200未満 | 2343.75〜4687.5 |
| high | 200以上512未満 | 4687.5〜12000 |

frequency配列には1024要素ありますが、この帯域集計で使うのは512未満です。別のローカル試験でビン700だけを255にすると、6帯域の出力はすべて0でした。配列の後半をこの集計が参照しないことを確認した結果で、周波数配列全体が空という意味ではありません。

特定のHz範囲に反応させたいなら、sampleRateとfftSizeから添字を求める設計へ変えます。その場合も、境界の丸め方やビン数が変わったときの平均の取り方を決める必要があります。今回、元コードは変更していません。

## ビート検出は時間単位も確認する

BeatDetectorは、直近60回までの振幅履歴を持ち、平均の1.3倍を超え、かつ0.05を超える値で反応します。反応後は8回の呼び出しを抑制する実装です。

ローカル試験では0.1を60回渡した後、0.5で反応し、その後の8回はfalseでした。この試験で確認したのは、履歴と待機期間がミリ秒ではなく呼び出し回数で決まる動作です。BPM推定は検証していません。

呼び出す頻度が変われば、同じ8回でも経過時間は変わります。音楽のテンポとして使うなら別の評価が必要です。この記事では描画フレームレートや、曲ごとの検出精度を測っていません。

## 描画へ渡す前に、値の意味を決める

全体の膨らみを音の振幅へ対応させるならRMS、瞬間的な強さならpeak、帯域ごとの反応なら周波数側の集計を使う、という分け方ができます。どれも同じ単位の「音量」とは扱いません。

確認したのは解析関数と合成音に対するWeb Audioの値です。アプリ全体の起動確認、マイク許可、ファイル再生、入力切替、長時間描画の負荷は今回の試験に含みません。実入力をつないだときは、モック表示との区別から確認を始めます。
