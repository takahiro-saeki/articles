Planeへ分類を追加する前に、既存のプロパティで何を検索できるかを確認します。今回調べたSquadNoteでは、ラベルは0件でした。それでも、状態と優先度は保存されていました。

「ラベルを増やしすぎたので減らした」という運用履歴は確認できません。ここでは現在の52件とGitの制作資料を読み、次にラベルを作るなら何を分類するかを決めます。実環境への追加や削除はしていません。

## まずラベル一覧とWork Itemの両方を見る

2026年9月11日、個人WorkspaceのSquadNote Projectからラベル一覧を取得しました。件数は0で、次ページもありません。WorkspaceのWork Item一覧を最後のページまで取得し、SquadNoteに属する52件を抜き出すと、全件のlabelsも空でした。

片方だけだと、設定がないのか、設定はあっても付けていないのかを区別できません。今回は両方を確認しています。

| 保存済みの分類 | 件数 |
| --- | ---: |
| Completed | 29 |
| Started | 6 |
| Backlog | 11 |
| Unstarted | 5 |
| Cancelled | 1 |
| 優先度High | 21 |
| 優先度Medium | 25 |
| 優先度Low | 6 |

状態の5行と優先度の3行は、同じ52件を別の軸で数えています。足して作業件数にはしません。完了や優先度は、ラベルがなくても検索の条件になります。[Work Itemのプロパティ](https://docs.plane.so/core-concepts/issues/properties)にも、State、Priority、Assignees、Labelsは別々の項目として定義されています。

この件数は取得時点の非アーカイブ一覧です。過去にラベルを削除したか、以前どんな運用だったかまでは分かりません。

## 技術名を、そのまま作業分類にしない

SquadNoteの[技術構成文書](https://github.com/takahiro-saeki/circle-hub/blob/770de5f2989775cfd95f7a9c4529565a2b48d2fd/docs/architecture.md)には、Web、API、DBなどの構成が書かれています。一方、[Instagram制作資料](https://github.com/takahiro-saeki/circle-hub/blob/e295f5cedf9f8989b36c9f308dee4dbd8cf64c3f/docs/marketing/instagram/001-invite-join/README.md)は、SQN-47へ戻るリンクと、HTML/CSSの編集データ、キャプション、altテキストを持っています。

この制作資料はGit履歴でも確認しました。初期制作から後続の運用文書へ更新されており、`index.html`の実体もあります。ただし、文書中のチェック項目をすべて実施済みとは読み替えていません。

HTMLやCSSをラベルにすると、アプリ画面の変更と投稿素材の制作が同じ集合に入ります。「CSSを使う作業を全部見たい」なら役に立ちますが、「公開素材をまとめて確認したい」という目的には別の分類が必要です。

技術構成文書の版を固定したのは、現在の依存バージョンを説明するためではありません。同じProjectに、アプリの構造と制作物の両方を確認する資料があることを根拠にしています。

## ラベル名より先に、繰り返し使う検索を書く

次の表は、これから分類を選ぶための案です。右端はすでに設定したラベルの一覧ではありません。

| 探したいもの | 最初に使う項目 | ラベルを足す判断 |
| --- | --- | --- |
| 優先して扱う作業 | Priority | 「緊急」というラベルは重ねない |
| 進行中の作業 | State / stateGroup | 「実装中」という同義ラベルは重ねない |
| 不具合の再現と修正 | 本文、必要なら作業種別 | 繰り返し一覧が必要ならkind:bugを候補にする |
| 投稿に使う制作物 | 対象資料と成果物 | 公開素材の確認用ならkind:contentを候補にする |
| 特定ライブラリの利用箇所 | リポジトリのコード・依存定義 | 各チケットへ技術タグを一括付与しない |

たとえばkind:contentを作るなら、「成果物が公開用の画像・動画・文章である」という付与条件も一緒に残します。単にHTMLがあるから付ける、という基準にはしません。bugも、機能追加のすべてへ付ける分類にはしません。

この2つで足りると実測したわけではありません。最初に試す候補であり、検索するときに本文を毎回読み直している範囲が他にあれば、別の軸を検討します。使用頻度を測っていない段階で、最適なラベル数を決めることはできません。

## 複数Projectへ広げる前に確認すること

[PlaneのWork Item Labels](https://docs.plane.so/core-concepts/issues/labels)では、ラベルはProjectに属します。同じ名前を別Projectへ用意しても、一つの共通ラベルとして扱えるとは考えず、各Projectの設定を確認します。状態、優先度、担当者で表せない分類を補う用途として読むと、重複した軸を減らせます。

整理するときは、名前が似ているという理由だけで削除しません。ラベルを使うViewがあるか、既存のWork Itemへどう付いているかを先に調べます。公式資料には、削除時に付与先やViewからも外れること、親ラベルの削除が子にも及ぶことが書かれています。今回は0件なので、この削除動作は実行していません。

採用後に確認する結果は、「一覧を開けば公開素材が揃い、状態や優先度の別管理を増やさずに済むか」です。まず一つのProjectの少数の実タスクで、必要なものが揃い、不要なものが入らないかを確認します。その結果を見て別Projectへの展開を判断する案です。

取得結果と集計コードは[調査記録](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/production/2026-09/batch-11/plane-analysis.json)に残しました。確認はPlaneの読み取りとPython 3.14.5の集計で行っています。ラベルによる検索時間の短縮や、実際の分類変更の効果は測っていません。
