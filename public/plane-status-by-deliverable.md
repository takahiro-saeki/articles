Planeで「確認待ち」を追加するときは、表示名を決める前に、その作業が完了済みかを決めます。確認が受け入れ条件に含まれるなら、表示名にかかわらず未完了のグループへ置きます。

個人用Planeのゲーム、演奏会、アプリの3プロジェクトを読み、状態名と所属グループを比較しました。状態の共通化で問題が起きたという記録は見つからなかったため、取得した設定を使い、確認待ちを追加するならどう分類するかを考えます。

## 現在の設定は、3プロジェクトとも同じだった

2026年9月11日に、個人用WorkspaceのDRG、RECITAL、SQNでStates一覧を取得しました。各応答の次ページなしを確認し、表示名、group、defaultを比較しています。ワークスペース全体の全プロジェクトを調べた結果ではありません。

| 表示名 | group | 初期状態 |
| --- | --- | --- |
| Backlog | backlog | はい |
| Todo | unstarted | いいえ |
| In Progress | started | いいえ |
| Done | completed | いいえ |
| Cancelled | cancelled | いいえ |

各プロジェクトは5状態で、表の組み合わせは一致しました。ただし、状態IDはプロジェクトごとに異なります。SQNで取得したDoneのIDを、そのままDRGの更新へ渡せるという意味ではありません。

「確認待ち」「公開待ち」という名前の状態は、この3件の一覧にはありませんでした。以下は新たに追加する場合の案であり、設定変更はしていません。

## 表示名よりgroupを確認する

[Planeの状態の説明](https://docs.plane.so/core-concepts/issues/states)では、完了として数えるのはCompletedグループです。独自の状態名を付けても、所属グループによる扱いは残ります。通常のプロジェクト設定とは別に、Enterprise GridのGovernanceで状態を管理する構成もあるため、変更できる場所は導入環境で確認します。

確認待ちをCompletedへ置くと、「確認が残っている」という名前と、完了としての分類が食い違います。逆に、要件を満たして終わった作業をIn Progressのままにすると、その作業自体の完了が記録されません。

アプリの開発と公開を同じ状態表で扱うときは、どこまでが一つのWork Itemなのかを先に読みます。

| 作業の受け入れ条件 | 現在地 | 状態の案 |
| --- | --- | --- |
| 開発環境で動作し、必要な端末確認まで終える | モバイル確認が残る | 確認待ち / started |
| 開発環境での確認までで、本番配布は範囲外 | 条件をすべて満たした | Done / completed |
| 記事を公開し、公開ページを確認する | 原稿だけできた | 公開待ち / started |

これは運用ルールの提案です。「公開待ちは必ずstarted」というPlaneの固定仕様ではありません。原稿作成だけのWork Itemなら、校正を終えた時点でDoneとし、公開を別の作業にできます。

## 実際の受け入れ条件で判定してみる

SQN-30は、体験参加者の権限と手動での昇格・終了を扱う作業です。取得した本文には、Web・iOS・Androidの一貫性が受け入れ条件としてあり、本番反映は対象外と書かれていました。Plane上の状態はIn Progressです。

関連する[固定commitの検証文書](https://github.com/takahiro-saeki/circle-hub/blob/0cda1e865ad80d1529197729d8d436e96d56edc7/docs/testing/sqn-30-trial-participant-checklist.md)には、Webの確認済み記録と、モバイル実機確認の未チェックが残っています。この記事ではアプリを再検証せず、文書とチケットを照合しました。

この条件なら、モバイル未確認を理由に確認待ちへ分ける案は成立します。しかし、本番配布を待たせる必要はありません。このWork Itemには含まれないからです。

状態名の点検には、次のような小さな一覧でも使えます。実データを書き換えるコードではなく、案の分類を確かめる例です。

```js
const proposed = [
  { name: "Ready for verification", group: "started" },
  { name: "Ready to publish", group: "started" },
  { name: "Done", group: "completed" },
];
const completedNames = proposed
  .filter(state => state.group === "completed")
  .map(state => state.name);
console.log(completedNames); // ["Done"]
```

ローカル実行では完了側に残るのはDoneだけでした。「Ready for verification」のgroupだけをcompletedへ変える比較では、その名前も結果に入りました。これは分類の例であり、Planeの画面上の割合や集計全体を再現したものではありません。

## 共通化するのは、名前より完了の判断

最初の点検では、各状態を使う条件を一文で書きます。「確認待ち: この作業の受け入れ確認が残る」と定義できれば、誰の確認が必要か、結果をどこへ残すかまでWork Itemで補えます。待つ相手が違うだけで状態を増やす必要はありません。

一方、ゲームの配布確認と、演奏会の当日運営を同じ「公開待ち」へ押し込むと、何を待っているのか読みにくくなります。表示名は成果物に合わせ、完了条件を満たすまでは完了へ分類しない、という判断を揃えます。

今回確認したのは3プロジェクトの現在の設定と、一つの実在する受け入れ条件です。状態を追加した後の使いやすさや、滞留時間の変化は測っていません。導入するなら、追加前に一つのWork Itemを選び、その状態へ入る条件と出る条件を説明できるかを確かめます。
