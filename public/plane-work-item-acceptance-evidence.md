「Web・iOS・Androidで同じ権限にする」は完了条件です。「Webでは確認したが、モバイル実機は未確認」は結果です。Codexへ実装を渡すPlaneの本文では、この二つを別々に書くと、何を満たすべきかと、何が残っているかを読み分けられます。

実在するSQN-30の本文と、関連リポジトリの検証文書を照合しました。今回はチケットを起票・更新せず、既存の記録から、作業を渡す本文に必要な情報を整理しています。

## 既存の本文には、範囲と停止位置が書かれていた

2026年9月11日に読み取ったSQN-30の題は「[Step 1] 体験参加者権限と手動昇格・終了を実装する」です。本文には目的、実装範囲、受け入れ条件、スコープ外の区分がありました。

確認した内容を、作業の判断に使う形へ縮めると次のようになります。

| 区分 | 本文にあった内容 |
| --- | --- |
| 権限の決定 | 招待種別をサーバー側で決め、URLの変更で権限を変えられない |
| 互換性 | 旧招待URLを維持し、確認後に明示的に無効化する |
| 昇格・終了 | 手動で正式参加へ変更でき、終了時は団体との関係だけを終える |
| 確認条件 | Web・iOS・Androidの一貫性、既存メンバーの回帰、自動テスト |
| 停止位置 | 開発環境と自動テストまで。本番DB・Web・ストアへ反映しない |
| 今回の対象外 | 新しい個別メッセージ、応募者管理、自動期限処理、本番リリース |

この本文は、開発環境で止めると明記しています。「実装してください」だけでは、開発環境の確認と本番での利用開始のどちらを求めているか決まりません。

ただし、今回取得した本文には、リポジトリURLや検証文書の固定commitへの参照はありませんでした。本文が具体的でも、次の担当者が調べる場所を一意に決められるとは限りません。

## 条件ごとに、どの記録が答えるかを見る

関連する[検証文書の固定commit](https://github.com/takahiro-saeki/circle-hub/blob/0cda1e865ad80d1529197729d8d436e96d56edc7/docs/testing/sqn-30-trial-participant-checklist.md)を読みました。文書の追加履歴は `12cbb78`で、今回の参照先は `0cda1e8`です。履歴の存在と、そこに記載された確認結果を分けて扱います。

文書にはWebの確認済み記録があります。一方、モバイル実機確認は未チェックでした。チケットの状態も、取得時点ではIn Progressです。

| 受け入れ条件 | 固定文書から読めること | 今回の記事調査での扱い |
| --- | --- | --- |
| 招待種別で権限を固定する | WebでのURLパラメータ変更の確認記録がある | 記録を確認。動作は再実行していない |
| 体験終了で団体との関係だけを外す | 終了後のログインと所属解除の確認記録がある | 記録を確認。動作は再実行していない |
| 各クライアントで権限差が一貫する | Webの記録と、モバイル実機の未確認がある | 全クライアントで確認済みとはしない |
| 本番へ反映しない | 作業の停止条件として定義されている | 完了のために追加配布を要求しない |

チェックの総数だけを見ると、この対応が消えます。自動テストが多く通っていても、未確認の端末に関する条件を満たしたことにはなりません。文書を読んだ今回の調査も、当時の検証を再実行したことにはなりません。

## 起票時には未実行の結果を作らない

新しく作業を渡すなら、次の順で本文を作れます。これは既存チケットを基にした提案で、自動読み取り用の特別なCodex形式ではありません。

```text
Purpose
  The behavior that this change should make possible.

Repository
  Repository URL, working directory, and the starting revision.

Scope
  The changes included in this work item.

Acceptance criteria
  Observable behavior for each role and client.

Verification plan
  Checks to run and the location for their results.

Current evidence
  Not run, or a reference to an existing result and its revision.

Stop point
  The environment where the work must stop.

Out of scope
  Changes that require separate work.
```

起票時に書けるのは、確認方法の予定までということがあります。その場合は結果を未実行にします。「テストを追加する」という作業予定を、「テスト成功」と同じ欄に入れないようにします。

開始後に結果を追記するときは、対象commit、環境、実施した確認、残った条件を揃えます。分岐が複数ある作業では、単に「確認済み」と書くより、「どの権限で、どの操作を、どのクライアントから実施したか」を残すほうが、次の確認を選べます。

## 本文から、同じ根拠へ戻れるようにする

[PlaneのWork Itemの説明](https://docs.plane.so/core-concepts/issues/overview)には、外部URLをLinksとして関連付ける機能があります。本文に短い結果を書き、詳しい検証記録への固定リンクを添える方法を取れます。この記事でリンクを追加したわけではありません。

参照は、リポジトリのトップだけで終えないほうが確認対象を絞れます。この題材なら、上記の検証文書のpathとcommitが必要です。起票時の開始commitと、検証を行ったcommitが異なる場合は、それぞれの役割を明記します。

開発用の招待URLやテストアカウントを、一般向けの説明へ複写する必要はありません。チケット本文で必要な結果を要約し、実行用の情報は適切なアクセス範囲の資料を参照します。今回の原稿にも、それらの情報は載せていません。

## 「完了にできるか」は、残った条件から判断する

照合の結果、SQN-30には範囲と停止位置があり、Gitには具体的な検証記録がありました。その一方で、取得した本文だけではその文書の固定版へ戻れず、文書にもモバイル実機の未確認が残っていました。

したがって、この調査を根拠にDoneへ変えることはできません。追加するなら、検証文書への参照と残っている条件を追記する案になります。実際の追記や実機確認はしていません。

次の担当者には、既存の根拠と、まだ答えのない受け入れ条件を渡します。確認済みの範囲を保ちながら、残りの作業を選ぶためです。
