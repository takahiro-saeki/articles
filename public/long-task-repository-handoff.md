長い記事制作を再開するとき、「68本できた」という引き継ぎだけでは次の作業を決められません。本文の検証が終わった68組のうち、URLまで確定した完成品は41組でした。残る27組は本文を書き直す対象ではなく、canonical URL待ちです。

会話を読み返さずにこの区別を復元できるか、制作台帳、原稿、検証結果を同じcommitから読み直しました。再開時に残すべきものを、実際の記事リポジトリで確認します。

## 常設の作業規約と、その時点の進捗を分ける

[OpenAIのAGENTS.md資料](https://learn.chatgpt.com/docs/agent-configuration/agents-md)は、全体とプロジェクトの作業規約を重ねて読み込む仕組みを説明しています。公開を行わない、個人用アカウントを確認する、といった継続的な制約を置く場所として使えます。

一方、今回の「完成41組」「次にどの候補を調べるか」は時点に依存する情報です。AGENTS.mdへ全実行ログを詰め込むより、進捗表から該当バッチの記録へ辿れる形にします。これはこの制作で採ったファイル構成で、Codexが任意の進捗JSONを自動的に再開する機能ではありません。

対象は2026年9月11日のcommit `6fe4649`です。[制作台帳](https://github.com/takahiro-saeki/articles/blob/6fe464919b7fba46d27395668d39d1e44b7f6964/production/2026-09/catalog.json)には候補ID、日英のファイル、事実確認、検証、状態があり、[進捗表](https://github.com/takahiro-saeki/articles/blob/6fe464919b7fba46d27395668d39d1e44b7f6964/ARTICLE_PRODUCTION_STATUS_2026-09.md)はそのデータから生成しています。

## 数字を読む前に、どの版の記録かを確かめる

作業ディレクトリでは最初に未コミット変更と現在のcommitを確認します。

```sh
git status --short
git rev-parse HEAD
```

過去の引き継ぎを検証するなら、対象版の台帳を明示して読みます。

```sh
git show 6fe4649:production/2026-09/catalog.json
```

今回の再集計では、候補90件、本文検証済み68組、完成41組、URL待ち27組、本文の検証が残る22件を復元できました。日英の各ファイルがそのcommitに存在することも確認しています。

その数字は当時の結果です。別のcommitで作業が進んでいれば、今の進捗として採用する前に再集計します。古いメモと一致しないことを、直ちに破損や作業のやり直しと判断する必要はありません。

## 引き継ぎには件数の根拠への入口を残す

今回、検証用に次の情報を持つ引き継ぎJSONの例を作りました。

| 記録 | 用途 |
| --- | --- |
| 基準commitとブランチ | どの作業状態を指すか |
| 本文検証・完成・URL待ち・残りの件数 | 異なる状態を同じ「完了」にしない |
| 根拠6ファイルのパスとSHA | 記録の欠落や差し替えを検出する |
| 未解決事項 | URLを得るために勝手に公開しない |
| 次の候補IDと再開時の確認手順 | 過去の本文を重複生成しない |

根拠6ファイルは、台帳、進捗表、直前バッチのレビュー、Humanizer監査、本文用検証結果、canonicalの完成ゲートです。[引き継ぎ例](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/production/2026-09/batch-12/handoff-example.json)は、この調査で作った提案であり、以前から配置されていた記録ではありません。

ここには「実行中」という文字列だけで処理の生存を表す項目を置いていません。プロセスやジョブがある場合は、そのハンドルを現環境で照会し、終了・実行中・不明を確認してから再開方法を決めます。今回のファイル照合から、外部ジョブが動いているかは分かりません。

## 古い記録や欠落を、成功扱いしないか試す

Pythonの検証では、固定commitから読み出す正常系に加え、引き継ぎや読み取り結果を変えた4条件を作りました。

| 条件 | 結果 |
| --- | --- |
| 基準commit、件数、根拠が一致 | 不一致なし |
| 異なるcommitを指定 | 版の不一致を検出 |
| 本文68組を完成68組と記録 | 件数の不一致を検出 |
| canonical検証の根拠が欠落 | 欠落を検出 |
| 根拠ファイルの内容が変化 | SHAの不一致を検出 |

正常系だけの検証では、読めるファイルが古い場合を見落とします。確認対象を意図的に変えたところで止まるかを確かめています。元のリポジトリからファイルを削除したり、過去commitを書き換えたりはしていません。

ただし、SHAが一致しても本文の技術情報が正しい証明にはなりません。検証JSONに成功と書かれているだけでも不十分です。再開に必要な結論について、何を実行した結果なのか、対象原稿の版に対応するかをレビュー記録から辿ります。

## 再開後の最初の作業を狭く決める

この記録から再開するなら、まず現在の作業ツリーと基準commitとの差を調べ、未着手の候補を確認します。URL待ち27組を新規執筆の列へ戻したり、未完了だからと既存原稿を消したりする必要はありません。

[再集計と5条件の検証コード](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/audit-production-batch12.py)は固定Gitデータを読みます。引き継ぎ形式の確認であって、Codexを別セッションで再起動して完走させた比較実験ではありません。所要時間の短縮や作業忘れの削減率も測っていません。再開者が根拠を読み直し、残る作業を選べる状態までを今回の確認範囲としました。
