日程を貼り付けて取り込めても、同じ入力を再実行して安全とは限りません。入力の解析、フォームへの反映、保存の再試行で、それぞれ結果が変わる可能性があります。

SquadNoteの実装を固定commitで読み、解析器、Webの反映処理、保存処理をローカルで動かしました。解析に成功しても、保存を再実行した結果まで同じとは限りません。特に年の省略と途中失敗は、重複行だけを除いても解決しません。

## 調べたのは、テキストを入力欄へ反映する機能

対象はcircle-hubのcommit `a34608c`です。[実装commit](https://github.com/takahiro-saeki/circle-hub/commit/68bcd9522a87b34445aac511f403fc9f7be84145)で、共通のテキスト解析器とWeb・モバイルの貼り付けUIが追加されています。[グロース資料](https://github.com/takahiro-saeki/circle-hub/blob/a34608c611ded6549c1176a7977e68e1bc62a8db/docs/growth/README.md)では、この施策の完了条件をLINE・メモ貼り付け、CSV、前月コピーのいずれかの提供としていました。

今回確認した経路はテキスト貼り付けです。CSVの列マッピングや、外部サービスとの同期処理を実装済みとして扱ってはいません。

[解析器](https://github.com/takahiro-saeki/circle-hub/blob/a34608c611ded6549c1176a7977e68e1bc62a8db/packages/schedule-text-parser/src/index.ts)は、各行の日付、開始・終了時刻、場所を取り出し、成功行とエラーを別々に返します。パッケージの版は0.1.0です。UIでは解析結果を確認して入力欄へ反映し、その後に通常の登録操作を行います。

検証環境は2026年9月11日のmacOS、Node.js 24.15.0、Asia/Tokyoです。実リポジトリは変更せず、固定Gitから取得したコードを使用しました。

## 年を省くと、同じ文字列でも翌年になる

最初に解析だけを確認します。リンク先の解析器を `schedule-text-parser.ts`として保存し、同じディレクトリに次の `check.mjs`を置きます。Node.js 24.15.0で `node check.mjs`を実行すると再現できます。外部ライブラリのインストールは不要です。

```js
import { parseScheduleText } from "./schedule-text-parser.ts";

const input = "9/10 19:00-21:00 A";
for (const baseDate of [
  new Date(2026, 8, 9, 12),
  new Date(2026, 8, 11, 12),
]) {
  console.log(parseScheduleText(input, { baseDate }).schedules[0].date);
}

const explicit = "2026/9/12 19:00-21:00 A";
const result = parseScheduleText(explicit + "\n" + explicit, {
  baseDate: new Date(2026, 8, 11, 12),
});
console.log(result.schedules.length, result.errors.length);
```

```text
2026-09-10
2027-09-10
2 0
```

実装は年がない場合、基準日から見て次に来る日付へ補完します。基準日より前の月日なら翌年になります。上の例では、入力に変化がなくても基準日が変わると結果の年が変わりました。

また、明示的な年を含む同じ行を2回渡しても、成功行は2件、エラーは0件です。解析器は重複行を取り除いていません。

同じ入力と同じbaseDateを渡した結果は一致しました。結果を比べる際は、基準日も解析の入力に含めて考えます。移行のやり直しなら、最初の基準日を保存するか、確定した年を含むデータから再開する設計が必要になります。これは今後の設計案です。

## 入力欄への再反映は、追記ではなく置き換えだった

[Webのフォーム](https://github.com/takahiro-saeki/circle-hub/blob/a34608c611ded6549c1176a7977e68e1bc62a8db/apps/web/src/app/%28app%29/organizations/%5Bid%5D/schedules/new/page.tsx)の `importParsedSchedules` は、解析結果から作った配列を `setRows`へ渡しています。既存の行との結合はしていません。

実際の関数を取り出し、状態更新先だけをメモリ上の配列に替えて確認しました。手入力行を置いた後に同じ1件を2回反映すると、最後の行数は1件です。元の手入力行は残りませんでした。

これは保存済み日程の重複を防いだ結果ではありません。編集途中の入力欄を置き換えた結果です。日付を手で直した後に再解析・再反映するなら、その修正を失う可能性を考える必要があります。

取得したUIコードでは、テキストを編集すると古い解析結果を消し、再解析を必要にしています。一方、フォームへ反映した後の編集内容まで、次の反映で統合する機能はありません。

## 保存の途中で失敗した場合も、別に調べる

[保存ルーター](https://github.com/takahiro-saeki/circle-hub/blob/a34608c611ded6549c1176a7977e68e1bc62a8db/apps/web/src/server/api/routers/schedule.ts)の `createBulk` は、各行へ新しいUUIDを付け、6行ずつ順番にinsertします。取得したこの処理には、取り込み要求を識別するキーや、前回成功した行を照合する分岐はありません。

この関数本体を取り出し、権限確認とDB書き込みなどの外部依存を代替処理にしました。7件を渡し、2回目のinsertだけを失敗させた後、同じ7件を再実行しています。

| 時点 | メモリ上に残った行数 | 異なる日付の数 |
| --- | ---: | ---: |
| 最初の6件が成功し、次のinsertが失敗 | 6 | 6 |
| 同じ7件を再実行した後 | 13 | 7 |

失敗前に残った6行へ、再実行分の7行が加わりました。UUIDも新しく作られるため、この試験では13行のIDがすべて異なります。

これは、実際の関数の制御フローを、成功したinsertが残るメモリ上の代替DBで確認した結果です。D1への接続、実ネットワークの切断、実アプリからの再送は試していません。D1の障害時の振る舞いを実測した表としては読めません。

それでも、フォームのボタンを送信中に無効にすることだけでは、この再実行を識別できないと分かります。途中で失敗した後に何を再送するかは、保存処理側の問題として残ります。

## ほかの境界も、成功件数とは別に見た

計8ケースで解析と反映・保存を確認しました。上記以外では、全角数字と「時」表記の正規化、不正な日付と逆転した時間範囲、場所が空の警告、件数上限を確認しています。

| 入力や条件 | 実行結果 |
| --- | --- |
| 全角の日付、18時30分相当から21時まで | 18:30と21:00へ正規化 |
| 存在しない日付 | invalid_date |
| 終了時刻が開始時刻より前 | invalid_time_range |
| 場所だけ欠ける | 成功行とlocation_missingの警告 |
| 同じ有効行を51行渡す | 成功50件、残りはlimit_exceeded |

上限は成功行数に対して判定されます。エラーを含む全入力行数と、保存候補の件数を同じ数字として扱わないようにします。

今回の試験は、あらゆる表記や日付の組み合わせを網羅したものではありません。抽出用の正規表現が文字列全体を検証するものか、別の文字の一部にも一致するかといった入力境界には追加試験の余地があります。

## 再実行できる設計にするなら

改善案は、解析時の基準日を固定すること、入力欄の置き換えを利用者へ伝えること、保存時の再試行を識別することです。今回、これらの修正は元リポジトリへ入れていません。

保存については、取り込み単位のキーと各行の識別情報をサーバーで扱い、再送が既存の処理なのか新しい入力なのかを区別する案が考えられます。部分成功を許すなら成功行を返し、まとめて成功させるなら使用するDBでその保証を検証する必要があります。同じキーで内容が変わった場合の扱いも決めます。

単純に「同じ日時・場所なら消す」とすると、意図的に同条件で作る別の日程まで消すおそれがあります。重複らしさだけで同一と決めず、何を一回の取り込みとするかを先に定義します。
