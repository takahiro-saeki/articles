日英の原稿が136ファイルあっても、136日分のストックにはなりません。同じ内容の日英は一組です。さらに、本文が検証済みでもcanonical URLが未確定なら、この制作ルールでは完成した一組に数えられません。

日数を出すには、使える組数と、一日にどの媒体へ何組出すかを決めます。今回は実際の制作台帳を読み、仮の公開枠へ割り当てるだけのローカル計算で確認しました。

## 集計するcommitと一組の条件を固定する

2026年9月11日に、`articles`のcommit `6fe4649`の[制作台帳](https://github.com/takahiro-saeki/articles/blob/6fe464919b7fba46d27395668d39d1e44b7f6964/production/2026-09/catalog.json)と原稿の存在を照合しました。対象は新規候補90件だけです。過去の公開済み記事はストックへ加えません。

| 台帳から確認した項目 | 件数 |
| --- | ---: |
| 本文・日英対訳・Humanizerまで検証済み | 68組 |
| その原稿ファイル | 136ファイル |
| URLを含めて完成した下書き | 41組 |
| canonical URL待ち | 27組 |
| 本文の検証が残る候補 | 22件 |

完成41組はすべてZenn向けでした。Qiita向け27組は記事IDが未確定です。これはQiitaへ原稿を用意できないという意味ではなく、この時点で日英のURLまで確定した組がない、という分類です。

68組を一日一組で割った68日と報告すると、URL待ち27組を利用可能な完成原稿へ混ぜてしまいます。

## 日数は公開枠の条件で変わる

完成したZenn 41組、完成したQiita 0組を在庫とし、次の4条件で割り当てました。すべて仮の条件で、実際の予約は作りません。

| 仮の公開枠 | 途切れずに埋められる日数 |
| --- | ---: |
| 毎日Zennを1組 | 41日 |
| 毎日Zennを2組 | 20日 |
| Qiitaから始めてZennと交互に1組 | 0日 |
| Zennから始めてQiitaと交互に1組 | 1日 |

二行目は41組のうち40組を使い、残る1組では次の日の2枠を埋められません。交互の予定では、Zennの在庫が多くてもQiitaの枠に来た時点で止まります。

「全媒体を合計した在庫÷平均頻度」では、この欠品を表せません。媒体の条件が固定なら、先の日付から必要数を引き当てます。

## 最初に埋められない日で止める

検証に使った関数です。`plan`の各要素は一日分の媒体別必要数で、件数は正の整数を渡す前提です。

```python
def covered_days(available, plan):
    remaining=available.copy(); days=0
    for needs in plan:
        if any(remaining.get(platform,0)<count for platform,count in needs.items()): break
        for platform,count in needs.items(): remaining[platform]-=count
        days+=1
    return days
```

この関数は足りない日の途中までを成功扱いしません。全枠を埋められるときだけ在庫を減らします。これで、原稿が足りる日が先頭から何日続くかを数えられます。

4条件は期待値と照合しました。ただし、個々の記事の鮮度、季節性、シリーズ順、同じ話題の連投はこの小さな計算には入っていません。媒体が合っていても、その日の読者に適した原稿とは限りません。

## 予約済みの日数は別に数える

同じcommitの[予約表](https://github.com/takahiro-saeki/articles/blob/6fe464919b7fba46d27395668d39d1e44b7f6964/schedule/publishing-schedule.json)は38行で、日付は2026年8月3日から9月9日でした。9月11日以降の行は0です。新規候補90件の原稿は、この予約表へ追加されていません。

したがって、この時点の結果は「完成原稿なら仮の条件で41日分」「将来の予約表には0日分」です。完成41組が予約済みになったわけではありません。また、過去の38行が全てその予定時刻に公開されたかは、この集計では調べていません。

台帳の本文検証、URL確定、予約表の割当を分けると、次の作業も変わります。本文が不足しているなら執筆へ、URLだけが未確定なら確定できる工程へ戻ります。予約しない方針の期間には、空の予約表を執筆不足と取り違えずに済みます。

[集計と4つの割当例](https://github.com/takahiro-saeki/articles/blob/codex/article-stock-2026-09/experiments/article-stock-2026-09/audit-production-batch12.py)はPythonで固定commitを読み、予約表を変更しません。この日数は投稿が成功する保証でも、執筆速度の予測でもありません。公開枠の条件を明示したときに、手元の完成原稿でどこまで埋められるかを示す値です。
